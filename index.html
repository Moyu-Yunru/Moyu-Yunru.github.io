使用 Hexo 写博客，并发布到 GitHub Pages

发表于 2026-05-23 分类于 学习笔记

Hexo 是一个静态博客框架。它的工作方式很适合初学者理解：我们用 Markdown 写文章，Hexo 把文章和主题模板组合起来，生成一组静态 HTML、CSS 和 JavaScript 文件。最后，把这些静态文件发布到 GitHub Pages，就可以拥有一个可以访问的网站。

一、准备环境

使用 Hexo 前，需要先安装两个基础工具：

  1. Node.js：用来运行 Hexo。
  2. Git：用来管理代码，并把博客推送到 GitHub。

这几步的意思是：

  1. hexo clean：清理旧的生成文件。
  2. hexo generate：重新生成 HTML 静态文件。

推送完成后，进入 GitHub 仓库的 Settings，找到 Pages 页面，确认发布分支设置正确。稍等一会儿，GitHub Pages 就会生成网站地址。

第一次部署时，我遇到了一个很典型的问题：hexo deploy 已经把 public/ 里的文件推送到了 GitHub 仓库，仓库根目录里也能看到 index.html、css/、js/、archives/ 等静态文件，但是浏览器访问：

对于 Hexo 这种已经生成好的静态网站，GitHub Pages 不需要再用 Jekyll 处理一遍。为了告诉 GitHub “直接发布这些静态文件就好”，可以在 Hexo 的 source/ 目录下放一个 .nojekyll 文件：

这样 hexo generate 时，.nojekyll 会被复制到 public/ 目录；hexo deploy 再把它一起推送到 GitHub。GitHub Pages 看到 .nojekyll 后，就会跳过 Jekyll 处理，直接发布 Hexo 已经生成好的静态网页。

如果后续再遇到 GitHub Pages 404，可以按这个顺序排查：

  1. 仓库名是否是 用户名.github.io。
  2. Pages 设置里的分支和目录是否是实际部署的位置，例如 main / (root)。
  3. 仓库根目录是否真的有 index.html。
  4. Actions 或仓库首页的 Checks 是否有失败项。
  5. Hexo 静态站点是否包含 .nojekyll。

这次问题解决后，我更清楚地理解了：hexo deploy 只是把文件推到 GitHub，真正让网站可以访问，还需要 GitHub Pages 成功完成发布流程。
