重新理解 Agent Skill：它不只是一个 Markdown 文件

发表于 2026-05-31 更新于 2026-06-09 分类于 AI与Agent 阅读次数：

前段时间面试时，我被问到一个问题：Skill 到底是什么？

我当时的第一反应是：Skill 不就是一个 SKILL.md 文件吗？这个回答不能说完全错，但明显太窄了。面试官接着追问：Skill 里面不是还可以有脚本吗？

这个追问一下子暴露了我当时理解里的盲区。我把 Skill 的入口文件当成了 Skill 的全部，却没有把它看成一个完整的能力包。后来我又读了一些关于 MCP、Tools、Skills 的材料，并自己动手做了一个 MarkItDown 转 Markdown 的工作流，才慢慢把这几件事串起来。

这篇文章就围绕这个问题展开：Skill 不是单纯的 Markdown 文件，而是一种让 Agent 按需加载知识、流程、脚本和资源的组织方式。

Skill 是一个面向 Agent 的能力包。它的核心入口通常是 SKILL.md，里面有名称、描述和使用说明；但它也可以包含脚本、模板和参考资料。Agent 会先根据元数据判断是否需要这个 Skill，再按需读取说明或运行脚本来完成任务。

二、Skill、MCP 和 Tools 分别解决什么问题

理解 Skill 时，很容易把它和 MCP、Tools 混在一起。它们都在扩展 Agent 能力，但所在层级不同。

可以先用三个问题区分：

Tools 是最小的执行单元。比如查询数据库、读取文件、调用浏览器、转换文档，本质上都可以包装成一个 Tool。Tool 通常有明确的输入输出 schema，执行结果也比较确定。

MCP 是连接层。它定义了一套协议，让不同 Agent 应用可以用统一方式发现和调用外部工具。没有 MCP 时，每个 Agent 应用都要分别对接每个工具；有了 MCP，工具可以通过标准协议暴露出来，Agent 客户端按协议调用。

Skill 则更偏知识层和流程层。它不一定直接提供一个外部接口，而是告诉 Agent：面对某类任务时，应该怎样判断、怎样拆解、怎样调用现有工具、什么时候运行脚本、什么时候提醒用户风险。

三、Skill 的关键设计：渐进式披露

Skill 有一个很重要的设计思想：渐进式披露。

四、为什么 Skill 里要放脚本

面试官问“Skill 里面不是可以有脚本嘛”，其实问到了 Skill 的一个核心价值：把确定性的复杂操作交给脚本，而不是每次都让模型临场发挥。

模型很擅长理解意图、做判断、写说明，但它并不适合把一堆细节操作都放在上下文里一步步手搓。比如：

  • 解析 HTML 中的所有图片来源；
  • 处理相对路径、根路径、协议相对路径；
  • 下载远程图片；
  • 判断 Content-Type 推断扩展名；
  • 避免文件名冲突；
  • 把 Markdown 里的远程图片链接替换成本地相对路径。

这些事情让 Agent 每次临时写代码都可以做，但不稳定，也浪费上下文。更好的方式是把它们写成脚本，放进 Skill 目录。

脚本带来的好处有三个。

第一，结果更确定。脚本经过测试后，同样输入更容易得到同样输出。

第二，节省上下文。Agent 不需要把几百行脚本内容全部读进上下文，只需要知道“这个脚本能做什么、参数是什么、运行后看结果”。

第三，便于复用和演进。以后需求变了，比如支持 srcset、支持 data:image、支持 DOCX 图片提取，只要改脚本和测试，不需要每次重新教 Agent。

所以 Skill 里的脚本不是装饰品，而是把“知识说明”变成“可执行工作流”的关键。

七、脚本如何补齐不同输入场景

我把输入类型拆成了几类。

URL 最适合做图片本地化。因为网页 HTML 里本来就有图片地址，脚本可以解析图片来源，下载到本地，再把 Markdown 链接改写成相对路径。

HTML 文件也类似。如果图片是本地路径，就复制到 assets；如果是远程 URL，就下载；如果是 data:image/png;base64,...，就解码保存。

PDF 则更复杂。MarkItDown 的 PDF 转换主要依赖文本和表格提取，不擅长保留嵌入图片及其位置。遇到“PDF 图片也要精确保留”的需求时，应该明确说明需要专门的 PDF 图片提取流程，而不是把普通转换包装成万能能力。

这几个分支也说明了一个点：Skill 不只是“工具说明”，它还可以承载策略判断。不同输入走不同路径，不确定能力要说明边界。

八、这件事给我的面试启发

如果面试官问“Skill 到底是什么”，只答“一个 Markdown 文件”是不够的。更完整的回答可以分三层。

第一层，SKILL.md 是入口。它定义 Skill 的名称、描述和核心指令，帮助 Agent 判断什么时候应该加载这项能力。

第二层，Skill 是目录级能力包。它可以包含脚本、模板、参考文档和示例文件。Agent 不一定一开始就加载全部内容，而是按需读取。

第三层，Skill 是工作流编排方式。它可以告诉 Agent 什么时候调用 MCP Tool，什么时候运行本地脚本，什么时候向用户说明限制。

九、我现在对 Skill 的定义

经过这次实践，我会把 Skill 定义为：

它至少有一个 SKILL.md，但不止于 SKILL.md。它可以包含：

  • 指令：告诉 Agent 任务边界和执行原则；
  • 脚本：把稳定流程变成可重复执行的程序；
  • 资源：提供模板、示例、参考文档；
  • 路由策略：决定什么时候用 MCP、什么时候用脚本、什么时候说明限制。

十、总结

这次面试问题让我意识到，很多 Agent 概念不能只看最表层的文件形态。

Skill 看起来是一个 Markdown 文件，但本质上是一个能力组织方式。SKILL.md 是入口，脚本和资源是扩展，渐进式披露是上下文管理方式，MCP 和 Tools 则是它可以调度的外部能力。

真正理解 Skill，要从“它是什么文件”走到“它怎样帮助 Agent 稳定完成一类任务”。当 Skill 里有脚本时，它就不只是提示词，而是把经验、流程和确定性代码打包成了一个可复用的 Agent 工作流。
