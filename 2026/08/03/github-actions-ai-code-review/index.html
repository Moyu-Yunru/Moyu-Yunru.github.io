把 AI 代码评审接入 GitHub Actions：从提交 Diff 到微信通知

发表于 2026-08-03 分类于 AI与Agent 阅读次数：

代码评审是研发流程里很重要的一环，但它也很容易因为时间紧、提交频繁而变成一句“看起来没问题”。如果能在代码推送后自动提取变更、调用大模型分析，并把结果归档下来，就可以先让机器完成一轮稳定的基础检查，再由开发者把注意力放到业务逻辑和架构决策上。

openai-code-review 就是围绕这个思路实现的一个 Java 组件。它目前以 GitHub Actions 作为执行入口：代码发生变更后，Workflow 下载并运行 SDK，SDK 获取最近一次提交的 git diff，调用 ChatGLM 生成 Markdown 评审报告，将报告提交到独立的 GitHub 日志仓库，最后通过微信公众号模板消息发送通知。

这篇文章会介绍组件当前的工作原理、完整接入过程、微信通知的特殊处理，以及后续如何把通知能力改造成可插拔接口。

一、组件解决了什么问题

传统代码评审一般依赖开发者主动创建 Pull Request，再由团队成员逐行检查。人工评审不可替代，但一些重复性问题很适合先交给大模型处理，例如：

  • 是否存在明显的逻辑漏洞和边界条件遗漏。
  • 异常处理、资源释放和空值判断是否完整。
  • 命名、注释与代码结构是否清晰。
  • 是否存在潜在性能瓶颈或安全风险。
  • 能否给出具体的修改建议和参考代码。

三、为什么当前主要依赖 GitHub Actions

SDK 本身是一个可执行 JAR，但它需要有人在合适的时机准备代码仓库和环境变量，然后启动它。当前这个“执行器”就是 GitHub Actions。

Workflow 主要承担五项职责：

  1. 监听 push 和 pull_request 事件。
  2. 检出代码，并保留足够的 Git 历史用于计算 diff。
  3. 准备 Java 运行环境并下载 SDK JAR。
  4. 从 GitHub 上下文和 Git 命令中提取项目、分支、作者与提交信息。
  5. 将 GitHub Secrets 转换成 SDK 需要的环境变量。

因此，这个组件并非只能在 GitHub 上运行，但当前接入模板、元数据提取、密钥管理和报告链接都围绕 GitHub 编写。如果换到 GitLab CI、Gitee Go、Jenkins 或其他平台，需要针对平台事件模型和环境变量做适配，不能原样复制 GitHub Workflow。

六、准备 ChatGLM 与微信配置

当前模型实现使用 ChatGLM，请求地址和 Key 通过环境变量注入：

配置项 示例或格式
CHATGLM_APIHOST https://open.bigmodel.cn/api/paas/v4/chat/completions
CHATGLM_APIKEYSECRET {id}.{secret}

CHATGLM_APIHOST 必须包含协议头，Secret 的值也不要额外包一层引号，否则可能出现 MalformedURLException: no protocol 或鉴权失败。

十、不需要微信通知时怎么办

当前版本的通知能力和主流程耦合得比较紧。入口会对全部环境变量做非空检查，这意味着四个微信变量只要有一个没有配置，程序就会在启动阶段抛出异常，评审流程也不会开始。

如果暂时不需要微信通知，可以给四个微信 Secret 填写非空的占位值。这样能够通过当前版本的启动校验。由于执行顺序是“先生成并推送报告，再发送微信”，报告通常仍可正常写入日志仓库。

不过，这种做法需要准确理解：

  • 占位值只是绕过“不能为空”的校验，并不是真正关闭通知。
  • SDK 仍然会请求微信接口，只是无效凭据无法产生有效消息。
  • 当前代码会打印微信接口响应，但没有解析并判断响应中的业务错误码，所以无效配置通常不会推翻已经完成的报告归档。
  • 如果微信接口出现网络异常或 HTTP 层异常，日志中仍可能记录代码评审执行错误。

因此，“填写占位值”只适合作为当前 v1.0 的临时兼容方式。更合理的设计是从模型上支持“不通知”，而不是用错误配置模拟关闭功能。

十一、更换 CI 平台时需要适配什么

如果要从 GitHub Actions 迁移到 GitLab CI、Gitee Go、Jenkins 等平台，SDK 的模型评审逻辑可以复用，但外围执行层至少要适配以下内容：

适配点 需要处理的内容
触发事件 将 push、pull_request 改为目标平台的 Push、Merge Request 或流水线事件
代码检出 确保存在足够的 Git 历史，能够取得父提交并计算 diff
提交元数据 将平台变量转换为 COMMIT_PROJECT、COMMIT_BRANCH、COMMIT_AUTHOR 和 COMMIT_MESSAGE
密钥管理 将 GitHub Secrets 改为目标平台的 Secret、Credential 或 CI Variable
JAR 分发 确保 Runner 能下载 Release 资产，或者改用制品库、容器镜像
仓库认证 根据平台调整 Token 权限、克隆地址和推送认证方式
报告链接 当前链接按 GitHub 的 /blob/master/ 结构拼接，其他平台需要重新生成

还有一个容易忽略的问题：当前评审粒度是“最近一次提交的 diff”，它不一定等于一个 Pull Request 或 Merge Request 的完整变更。迁移平台时最好把“如何选择比较基线”抽成适配接口，分别支持单次提交、两个 SHA 之间的变化，以及整个 PR/MR 的变化。

十二、下一版本：把通知抽象成独立接口

当前抽象服务直接依赖 WeiXin，主流程也固定调用微信发送方法。这会带来两个问题：不需要通知时仍被迫配置微信参数；新增钉钉、飞书或邮件时，需要修改已有业务流程。

下一版本可以把通知能力抽象为 INotification：

默认值可以设为 none。这样不配置通知时就自然使用 NoOpNotification，只生成报告而不发消息；只有选择 weixin 时才校验 WEIXIN_APPID、WEIXIN_SECRET、WEIXIN_TOUSER 和 WEIXIN_TEMPLATE_ID。以后增加新渠道，只需要新增实现类和对应配置，不必修改代码评审的主流程。

这个改造还可以顺便明确失败策略：

  • 获取 diff、调用模型或写入报告失败，属于核心流程失败，应该让 CI 返回失败状态。
  • 通知发送失败，默认只记录错误，不影响已经生成的报告。
  • 对通知要求严格的团队，可以再增加 NOTICE_FAILURE_STRATEGY=strict，决定是否让通知失败影响流水线。

这比简单增加几个 if 判断更稳定，也让“代码评审”和“消息触达”成为两个边界清楚的能力。

十三、当前版本还可以继续改进什么

除了通知接口，组件下一步还可以从几个方面继续完善：

  1. 将 Git 平台差异抽成接口，不再固定拼接 GitHub 的仓库和报告链接。
  2. 支持指定 base SHA 和 head SHA，准确评审完整 PR/MR，而不仅是最近一次提交。
  3. 区分核心流程异常与通知异常，让 CI 状态真实反映评审是否成功。
  4. 对微信等外部接口的响应体做业务错误码校验，并输出更明确的错误信息。
  5. 为不同类型的环境变量增加分组校验，只校验当前启用能力真正需要的配置。
  6. 增加报告大小、diff 大小和敏感文件过滤，避免超长请求或不必要的信息外发。

十四、总结

openai-code-review 的核心价值，不只是调用一次大模型，而是把“获取变更、生成评审、归档结果、通知开发者”串成了一条可以重复执行的工程流程。

当前版本借助 GitHub Actions 已经能够以较低成本接入其他 GitHub 仓库：准备日志仓库和 Token，配置模型与微信 Secrets，复制 Workflow，推送代码即可触发。但也要认识到现阶段的边界：执行入口依赖 GitHub Actions，评审对象是最近一次提交，微信参数形式上必填，通知也还没有与主流程解耦。

下一版本引入 INotification 和 NoOpNotification 后，“不通知”会成为系统正式支持的一种策略；微信、钉钉、飞书和邮件则只是可替换的实现。再进一步抽象 Git 平台和 diff 选择方式，这个组件就能从一个 GitHub Actions 工具，逐渐演进为更通用的自动代码评审基础设施。
