AI 写 SQL 不能只问“怎么查”：一次 N+1 查询优化复盘

发表于 2026-06-18 更新于 2026-07-02 分类于 后端工程 阅读次数：

用 AI 辅助写后端代码时，我遇到过一个很典型的问题：如果提示词只写“帮我实现这个接口”或者“帮我写一段 SQL 查出这些数据”，AI 通常能把功能写出来，但它不一定会关心这段 SQL 执行多少次、会不会慢、数据量变大后还能不能扛住。

这次智慧调度需求里，getMonitoring 和 initiateDispatch 两个接口就暴露了这个问题。功能上看，接口能返回泵站监测数据、摄像头编码、预警状态、上游泵站和建议操作；但性能上看，里面隐藏了大量循环查库。局域网环境下可能没感觉，一旦数据库连接切到 VPN 环境，单次查询延迟被放大，接口响应就从“还能接受”变成了接近不可用。

这篇文章不展开所有业务细节，只复盘一个核心教训：让 AI 写 SQL 时，不能只要求功能正确，还要把性能约束写进提示词和验收标准。

一、功能正确不等于工程正确

getMonitoring 是一个运行监测接口。前端传入区域类型，比如泵站 bz，后端要返回该区域下所有泵站的实时数据：

  • 泵站名称、坐标、在线状态；
  • 当前液位、瞬时流量等公共指标；
  • 每台泵机的运行状态、运行模式、电流、电压等指标；
  • 是否预警、预警类型；
  • 摄像头编码和最新数据时间。

initiateDispatch 是发起调度初始化接口。前端传入一个预警泵站终端编号，后端要返回当前泵站、上游泵站以及每台泵机的建议操作。

从功能角度看，这些逻辑都能拆成一个个小查询：

如果只是让 AI “把数据查出来”，它很容易写出一种直觉式实现：先查一批基础数据，然后在循环里继续查每个传感器、每个终端、每条规则对应的数据。

这种写法最大的问题是，它看起来非常顺。

当数据量小、数据库就在局域网里、单次查询只要 1ms 时，这种代码甚至不会马上暴露问题。但它的风险一直存在，只是被低延迟掩盖了。

二、N+1 是怎么被放大的

这次接口涉及多个数据源：设备和传感器配置在一个库，实时数据在另一个库，摄像头和调度配置又在 SQL Server 里。

优化前的大致调用方式可以抽象成这样：

  1. 先查一次设备和传感器配置。
  2. 遍历每个传感器，逐条查询 data_latest，用来计算最新数据时间。
  3. 遍历每个终端，逐条查询摄像头编码。
  4. 组装返回值时，再遍历每个传感器，逐条查询 data_latest 取实时值。
  5. 计算预警时，再按设备查询当前液位。

如果有 100 个传感器、20 个终端、10 个设备绑定了预警规则，数据库调用次数大概会变成：

这就是典型的 N+1 问题。更准确地说，它不只是一个 N+1，而是多个 N+1 叠在一起。

真正让问题爆炸的是环境变化。原来局域网里单次 SQL 很快，后来切到 VPN 链路，单次查询延迟可能到几百毫秒。假设一次数据库往返 300ms，200 多次调用理论上就会被拉到一分钟级别。

这时再看原来的实现，就会发现问题不是“某条 SQL 写得特别慢”，而是“数据库往返次数太多”。

六、代码审查时重点搜什么

如果已经让 AI 写完了代码，我会重点检查几类信号。

第一，搜索循环里的 Mapper 调用：

不是说循环里调用 Mapper 一定错，但它一定值得追问：这是不是可以批量查？如果循环次数从 10 变成 1000，会发生什么？

第二，检查同一张表是否被重复查。比如这次 data_latest 同时被用来取最新时间、实时值和预警计算。如果每个步骤都各查一遍，就是典型浪费。

第三，检查接口之间是否重复跑完整流程。一个接口调用另一个重接口多次，很容易让数据库调用成倍增长。

第四，把环境延迟算进去。性能评估不能只看本地开发库。只要数据库在远端、跨网络或走 VPN，数据库往返次数就会变成核心指标。

七、总结

AI 能很快写出一段“能跑”的 SQL，但后端接口不是只要能跑就行。数据量、调用次数、网络延迟、索引和复用方式，都会决定这个接口上线后是稳定还是拖垮页面。

这次优化给我的经验可以概括成一句话：

功能正确是第一步，性能正确才是能交付的后端代码。
