一次博客评论延迟加载排查：Codex、Chrome 插件和 Skill 是怎么配合的

发表于 2026-06-09 分类于 AI与Agent 阅读次数：

今天在浏览自己的博客时，我发现了一个很小但有点别扭的问题：打开一篇文章，翻到最底部之后，评论区不是立刻出现，而是停顿一会儿才冒出来。

这个问题本身并不严重。评论功能能用，页面也没有报明显错误。但它很适合作为一个排查样本：现象发生在浏览器里，配置藏在 Hexo 和 NexT 主题里，真正的评论系统又是第三方的 utterances。以前遇到这种问题，我大概率会在浏览器开发者工具、主题配置、生成后的 HTML 之间来回切。

这次我直接把线上链接丢给 Codex，让它结合当前项目排查：

结果比我预期快很多。它不是只在代码里搜关键词，也不是只凭经验猜“应该是懒加载”，而是把 Chrome 插件、项目源码和 Skill 里的调试流程串在了一起。

一、问题看起来很小，但需要现场复现

我的描述其实很口语化：评论功能“不是立刻出现，而是过一会再出现”。

这里面有几个可能性：

  1. utterances 服务本身加载慢；
  2. GitHub 相关请求慢；
  3. NexT 主题对评论做了懒加载；
  4. 评论容器被动画或 CSS 延迟展示；
  5. 生成后的线上页面和本地配置不一致。

如果直接改配置，很容易变成“凭感觉修”。Codex 先做的是复现现场。它通过 Chrome 插件打开线上文章，然后观察页面初始状态：评论容器已经在 DOM 里，但里面没有 utterances 的脚本，也没有 iframe。

接着它滚动到页面底部，并记录评论区的变化。这个时间线很关键：

看到这里，问题已经不像是“评论服务随机慢”，更像是“滚动到底部后才开始加载评论脚本”。也就是说，用户看到的那段等待，不只是网络耗时，而是加载动作本身被推迟了。

二、Skill 让 Codex 先找根因，而不是先猜修法

这次让我感觉明显不一样的地方，是 Codex 使用了系统化调试相关的 Skill。

Skill 在这里不是一个很玄的概念，它更像一份流程约束：遇到 bug 或异常行为时，先复现、收集证据、追数据流，再谈修复。这个顺序听起来朴素，但对排查很重要。

三、Chrome 插件负责看现场，源码搜索负责追实现

Chrome 插件解决的是“线上页面实际发生了什么”。它可以打开用户给的页面，滚动到底部，读取 DOM 状态，确认脚本和 iframe 是什么时候出现的。

五、这次体验让我重新理解插件和 Skill 的价值

我以前对 AI 编程工具的期待，更多是“帮我写代码”或“帮我解释代码”。但这次排查让我感觉，Codex 更像是在补齐一个工程师排查问题时的上下文切换成本。

这类问题本来要做几件事：

  1. 打开线上页面；
  2. 滚到底部复现；
  3. 看评论 DOM 有没有出现；
  4. 看脚本什么时候插入；
  5. 回项目里搜评论配置；
  6. 读主题工具函数；
  7. 对照生成后的 HTML；
  8. 给出结论和可能的修改方式。

每一步都不难，但它们分散在浏览器、终端、源码、构建产物之间。真正耗人的不是某一行代码，而是来回切换和保持上下文。

Chrome 插件让 Codex 能看到真实页面，而不是只根据仓库猜。Skill 让 Codex 按调试流程推进，而不是上来就给修复建议。项目上下文让它知道这是一个 Hexo 博客，评论配置应该从 source/_data/next.yml 和 NexT 主题里找。

这些能力拼在一起，才有了这次很快的排查体验。

总结

这次小问题让我对 Codex 的使用方式有了一个更具体的认识：它不只是一个代码生成器，更像一个能调用浏览器、理解项目结构、遵循调试流程的协作对象。

Chrome 插件解决“看见现场”，Skill 解决“按流程思考”，项目源码解决“找到根因”。当这三件事连起来时，一个原本需要我在多个工具之间切换的问题，就变成了一次很顺滑的对话式排查。

这可能才是 Agent 工具最有意思的地方：它不是替我拥有判断，而是把那些繁琐但必要的排查步骤组织起来，让我更快地看到问题真正在哪里。
