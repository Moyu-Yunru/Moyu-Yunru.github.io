用 Development Workflow Orchestrator 串联 DDD Skill 开发工作流

发表于 2026-07-09 更新于 2026-07-11 分类于 AI与Agent

前两篇文章分别讲了两件事。

第一篇是 OpenSpec 和 Superpowers 怎么配合：当需求比较大时，先用 OpenSpec 生成设计、任务和规范，再用 Superpowers 约束设计验证、TDD、实现和代码审查。

第二篇是 scenario-thinking 怎么用于二次开发：当需求没有大到需要完整流程，但业务边界又不能靠 AI 自己猜时，先做场景穷举和数值推演，再按推演文档实现。

这篇可以看作前两篇的总结和进一步落地：我们不应该只问“用哪个模型”，而应该先问“这个需求该走哪种开发模式”，再决定需要调用哪些 Skill。

这就是 Harness 的位置。

Harness 不是一个具体工具

Harness 直译有“马具、缰绳”的意思。放到 AI 编码里，它不是某一个固定插件，也不是某一个模型能力，而是一类工程化约束手段。

我更愿意这样理解它：

用户给 AI 的原始输入通常很短，比如“帮我改一下这个接口”“新增一个工具类”“按需求文档完成这个功能”。这类输入对人来说可以继续追问，对模型来说却很容易变成发散空间。

Harness 要做的事情，就是把模糊目标变成明确过程：

  • 先判断需求体量；
  • 再判断是全新需求还是现有代码二开；
  • 然后选择裸模型、scenario-thinking 或 OpenSpec/Superpowers；
  • 最后把 AI 约束在选定模式里完成交付。

所以 Harness 的价值，不是让模型突然“变聪明”，而是减少模型需要临场猜测的部分。

为什么它能缩小模型差距

不同模型之间的差距，很多时候不是体现在“会不会写一个 if”，而是体现在更前面的判断上：

如果用户只说“我要吃饭”，中间有太多信息需要补：什么时候、在哪、和谁、预算多少、忌口是什么。模型越强，越可能补得合理；模型弱一点，就更容易发散。

模型之间的差距就会缩小。因为很多需要推断的东西，已经被外部过程补足了。

AI 编码也是一样。Harness 的本质是把“请你猜”改成“按这个流程判断、按这个文档实现、按这些场景验证”。

它主要降低三类风险：

  • 意图推断风险：通过需求体量和类型判断，减少模型自己猜模式；
  • 推理发散风险：通过场景推演、设计文档和任务清单，把推理步骤外化；
  • 实现越界风险：通过模式隔离和完成标准，限制 AI 随意扩展范围。

Development Workflow Orchestrator：先选择开发路线

为了让 Harness 真正生效，我把模式判断和 Skill 调用规则整理成 DEVELOPMENT_WORKFLOW_ORCHESTRATOR.md，并将它命名为 Development Workflow Orchestrator（研发工作流编排器）。它可以放在 Workspace AI Rules 或 Project Rules 中，作为所有开发需求进入项目后的顶层调度规范。

这个编排器本身不负责场景推演、设计或编码。它只负责三件事：判断需求体量、识别需求类型、选择并锁定开发模式。具体工作再交给对应 Skill。

编排器会把需求分到三条路线里。

第一条是裸模型模式。

它适合非常小的 0 到 1 需求：新增一个工具函数、补一个简单转换方法、写一个不涉及复杂业务分支的小能力。这类需求如果也强行走完整设计流程，反而会把简单事情做重。

第二条是 scenario-thinking 模式。

它适合中小体量需求，尤其适合现有代码二开。原因很简单：二开最怕误伤旧逻辑。看起来只是新增一个标识、放开一个校验，背后可能会影响 null、false、旧调用方、特殊类型、混合明细、多轮调用等一串场景。

第三条是 OpenSpec/Superpowers 模式。

它适合大体量需求：改动跨多个模块，涉及多条主流程和异常流，需要明确设计、任务、测试约束和代码审查。这时完整流程虽然重，但它能把风险压住。

可以粗略记成：

先判断体量，再判断类型

Harness 的第一步不是调用 Skill，而是做模式选择。

需求体量可以按四个维度判断：

维度 小 中 大
改动文件数 3 个以内 3 到 8 个 超过 8 个
业务场景 单一无分支 2 到 5 个场景 多条主流程和异常流
模块依赖 基本无跨模块 1 到 2 个模块 跨多个模块或服务
预估时间 30 分钟以内 30 分钟到 2 小时 超过 2 小时

这里有一个保守原则：

这不是为了显得流程严谨，而是因为低估需求体量的代价很高。一个实际需要设计和测试约束的需求，如果误判成“随手一改”，后面通常会付出更多返工成本。

二者最大的区别是：0 到 1 更关注“怎么建”，二开更关注“旧行为不能坏”。

模式选择矩阵

把体量和类型合起来，可以得到一个简单矩阵：

需求类型 体量小 体量中 体量大
0 到 1 需求 裸模型，可选 scenario-thinking 推荐 scenario-thinking 强制 OpenSpec/Superpowers
现有代码二开 强制 scenario-thinking 强制 scenario-thinking 强制 OpenSpec/Superpowers

这个矩阵是前两篇文章的真正合流点。

scenario-thinking 不是只给中型需求用的。只要是现有代码二开，即使体量看起来小，也建议先推演。因为二开不是看“改几行代码”，而是看“有没有旧行为兼容风险”。

OpenSpec/Superpowers 也不是所有需求都要用。它适合大需求，但不适合每个小工具函数。流程是用来降风险的，不是用来制造仪式感的。

小需求：可以让模型直接做

比如新增一个获取当前时区的工具方法，逻辑单一，改动文件少，也没有复杂业务分支。

这类需求可以直接进入裸模型模式：

但裸模型模式也不是“完全放飞”。它仍然有边界：

  • 不做无关重构；
  • 不扩展需求外功能；
  • 实现中发现复杂度上升，要暂停并重新评估模式；
  • 能跑验证就跑验证。

裸模型适合的是“清楚、短、小”的任务，不适合“看起来短，但业务含义复杂”的任务。

二开需求：优先 scenario-thinking

如果需求是“在已有接口上补一个标识”“放开某个校验”“调整已有数量计算”，就不要急着写代码。

这类需求最容易出现的问题是：AI 只实现了新场景，却破坏了旧场景。

这些问题不问清楚，代码实现很容易看起来正确，实际语义却偏了。

大需求：进入完整流程

如果需求涉及多个模块、多条流程、多个页面或接口，甚至还包含权限、状态机、任务拆解、数据模型等内容，就应该进入 OpenSpec/Superpowers 模式。

这时完整流程的价值会变得明显。编排器把 OpenSpec/Superpowers 模式拆成六个 Phase：

Phase 触发或 Skill 主要职责
Phase 1 /opsx:propose、openspec-propose 生成 proposal、design、tasks、spec，并写入 DDD 分层约束
Phase 2 /opsx:apply、brainstorming 检查 OpenSpec 产物完整性，探索项目并确认实现方案
Phase 3 subagent-driven-development、TDD 根据设计定义测试，建立 RED-GREEN-REFACTOR 约束
Phase 4 openspec-apply-change 读取设计、任务和测试结果，按任务增量实现
Phase 5 requesting-code-review、receiving-code-review 发起增量审查，验证反馈并逐项处理
Phase 6 最终验证与交付 运行完整测试、检查任务状态、清理并报告结果

这里最需要强调的是 /opsx:apply。在编排器的规则里，它不是一个单独的实现命令，而是 Phase 2 到 Phase 4 的完整流程触发器：

收到 /opsx:apply 后，不能直接加载 openspec-apply-change 写代码。只有设计验证和 TDD 阶段都满足完成标准，才能进入增量开发；开发完成后，还要继续执行代码审查和最终交付。

这条路线重，但适合重需求。它把“需求分析、详细设计、任务拆解、测试约束、代码审查”都放进流程里，降低大需求里最常见的两个问题：范围漂移和实现不完整。

模式隔离很重要

Harness 里还有一条容易被忽略的原则：一旦选定模式，就不要随意中途切换。

原因是不同模式的上下文组织方式不同。

裸模型模式没有设计文档；scenario-thinking 有推演文档；OpenSpec/Superpowers 有 proposal、design、tasks、spec 和测试约束。如果中途随意切换，AI 很可能丢失前一个模式里的关键前提。

这也意味着 scenario-thinking 不会在完成后自动转入 OpenSpec。两者是由编排器选择的不同模式，不是一条固定流水线。

当然，模式不是永远不能升级。如果执行中发现体量被严重低估，应该暂停，说明原因，再征得用户确认后重新按更重的模式走。

一个比较稳的规则是：

这些 Skill 做了哪些 DDD 定制

编排器解决的是“什么时候调用”，Skill 解决的是“调用以后怎么做”。为了让这套流程更适合当前 DDD 后端项目，我对部分 Superpowers Skill 做了调整，并新增了 OpenSpec 与 scenario-thinking 相关能力。

对比原版 Superpowers 目录后，可以把变化分成三类：

类型 Skill 主要变化
新增并定制 openspec-propose 在标准 OpenSpec 产物后追加 DDD 详细分层设计
新增 openspec-apply-change 读取设计、任务和测试约束，按任务增量实现
原创 scenario-thinking 在编码前完成场景穷举、数值推演和详细设计

OpenSpec：让 design.md 约束代码分层

通用 OpenSpec 的 design.md 主要回答上下文、目标、技术决策、风险和迁移方案。这些内容能说明“为什么这样设计”，但还不足以约束代码必须落到哪个层级。

它还要求设计文档明确：

  • AppService 负责流程编排，并通过 Context 传递一次业务处理的数据；
  • DomainService 拆分业务阶段，DomainAbility 承载具体领域能力；
  • Repo、RPC、MQ 等外部依赖收敛到 Infrastructure；
  • 类名遵循 CmdAppService、QryAppService、DmService、Ability、Ops 等约定；
  • 核心模块需要给出调用链、类结构、方法签名和分层统计。

这样，design.md 就从普通架构说明变成了可以约束代码落位的实现蓝图。

需要说明的是，L0-L4 不是所有 DDD 项目的通用标准，而是当前团队对 DDD 的具体落地方式。这里定制的是“项目的 DDD 架构规范”，换一个项目后，层级、注解和命名规则都可能需要替换。

scenario-thinking：先找到规则，再决定模型

scenario-thinking 不是从 Superpowers 修改而来，而是独立编写的 Skill。它不会直接生成聚合、实体和值对象，而是先提供领域建模需要的业务材料：

推演结果 对 DDD 设计的帮助
业务对象与关键标识 形成统一领域术语，辅助判断聚合边界
正常、边界和异常场景 定义领域行为和验收条件
多轮调用与状态变化 识别状态机、幂等和生命周期规则
数值公式与决策条件 提炼业务不变量
现有逻辑的零改动范围 明确兼容边界

这里真正有价值的是“先推演，再建模”。如果直接让 AI 根据类名画领域模型，它很容易猜错边界；先用业务场景验证规则，再决定行为属于实体、领域服务还是应用编排，设计会可靠得多。

Harness 和模型选择的关系

原始材料里花了不少篇幅比较不同模型在三种模式下的表现。博客里我不展开具体评分，因为分数会随模型版本、项目代码、提示词和测试样本变化。

更值得保留的是这个结论：

当输入很模糊、流程很松散时，强模型的优势会很明显，因为它要承担更多隐性推理和补全工作。

但当 Harness 把需求分流、场景推演、设计文档、任务拆解和验证标准都外化以后，成本更友好的模型也能在许多日常开发任务里稳定工作。它未必在所有维度都超过强模型，但足够多的风险已经被流程提前吸收。

这也是 Harness 真正有意义的地方：它不是幻想用流程消灭模型差距，而是把“需要模型自由发挥的部分”尽量压缩到合理范围。

仍然无法完全抹平的差距也要承认：

  • 训练数据决定的知识边界；
  • 极深推理链上的稳定性；
  • 指令遵循和细节把控；
  • 对陌生技术栈的真实理解。

把 Workflow Orchestrator 接入 AI Rules

如果要把 Harness 落成 DEVELOPMENT_WORKFLOW_ORCHESTRATOR.md，我会保留四类内容。

第一，模式选择标准。收到需求后，先评估体量和类型，再说明为什么选择某个模式。

第二，三条模式的执行流程。裸模型、scenario-thinking、OpenSpec/Superpowers 要有清晰边界，选定后必须锁定模式。

第三，阶段门禁和禁止事项。比如现有代码二开不能直接用裸模型，大需求不能跳过设计，/opsx:apply 不能直接等价于写代码。

第四，异常处理。比如推演覆盖不了场景怎么办，scenario-thinking 过程中发现是大需求怎么办，OpenSpec 设计不完整怎么办。

规则不用为了完整而无限增长。真正重要的是让 AI 在关键分叉点上不乱选，并且让 OpenSpec 模式中的每个 Phase 都有清楚的完成标准。

开源与使用方式

目前，这套定制 Skill 已经开源到 Moyu-Yunru/development-workflow-skill。如果要在自己的项目中使用，可以先根据项目架构调整 DDD 分层、类命名和工具调用方式，再把 Workflow Orchestrator 放进项目级 AI Rules。

总结

Harness 可以理解成 AI 编码里的模式选择器，而 Development Workflow Orchestrator 是这个选择器的具体实现。

它不追求所有需求都走最完整的流程，也不放任所有需求都无约束推进。它做的是按风险分层：

在这套结构中，编排器负责调度，定制 Skill 负责把场景、DDD 设计、测试和审查真正执行下去。

对我来说，Harness 最重要的价值不是省 token，也不是替换强模型，而是让 AI 编码从“模型单点能力”变成“编排器调度 + Skill 能力 + 验证证据”的组合能力。这样项目越复杂，流程的收益越明显。

补充篇：用 scenario-thinking 把二次开发先推演清楚

发表于 2026-07-08 更新于 2026-07-10 分类于 AI与Agent

上一篇文章里，我整理了 OpenSpec 和 Superpowers 的组合方式：先把需求变成设计产物，再用流程纪律约束 AI 按步骤实现。

那套方式适合中等以上复杂度的需求，尤其是从 0 到 1 做一个新能力时，它能把 proposal、design、tasks、spec 都沉淀下来，后续实现和审查都有依据。

但实际开发里还有另一类很常见的任务：现有接口或现有方法上做一个看起来不大的二次改造。

比如只是新增一个标识、放开一个校验、调整一段数量计算、补一类特殊状态。直接让 AI 写代码，它可能马上动手；完整走一遍 OpenSpec，又显得有点重。这个中间地带，就很适合引入 scenario-thinking。

什么时候适合用 scenario-thinking

我会优先在这些场景使用它：

  • 改造已有接口或已有方法；
  • 业务规则看起来简单，但边界很多；
  • 涉及金额、数量、额度、库存、状态机；
  • 有“旧逻辑保持不变，新逻辑部分放开”的兼容要求；
  • 需要明确 null、0、负数、极大值、混合明细等边界；
  • 用户自己也不确定所有派生场景，需要 AI 帮忙追问。

反过来，这些场景不太需要它：

  • 纯文案修改；
  • 简单字段透传且无业务分支；
  • 明确的 CRUD 页面或接口；
  • 已经有完整测试覆盖的小重构；
  • 需求目标本身还很发散，连业务对象都没确定。

它真正约束了什么

scenario-thinking 表面上是在列场景，实际上是在约束 AI 的三个习惯。

第一，约束“马上开始写”。看到 /thinking 后，AI 的第一动作应该是理解、搜索、确认和推演，而不是编辑代码。

第二，约束“只覆盖主流程”。它要求正常、边界、异常、多轮、组合场景都被看见，尤其是旧逻辑兼容和新逻辑核心场景要同时覆盖。

第三，约束“用模糊词带过”。每个数字都要能追溯到公式，结论不能只写“符合预期”，必须说明为什么符合。

这也是它适合作为上一篇补充的原因。OpenSpec 和 Superpowers 让 AI 的开发流程更稳，scenario-thinking 则让 AI 在进入开发前先把复杂业务规则想清楚。前者解决“怎么交付”，后者解决“到底该交付什么行为”。

OpenSpec 和 Superpowers 怎么配合：给 AI 编码加一层流程护栏

发表于 2026-07-07 更新于 2026-07-10 分类于 AI与Agent

AI 编码用多了以后，很容易遇到一个微妙的问题：它确实能写代码，但不一定总是按我们希望的方式写。

有时候需求还没澄清，它已经开始实现；有时候设计文档写得很完整，真正落代码时却只看任务清单；还有时候明明应该先写测试、先确认边界，它会为了“快点完成”直接跳到编码阶段。最后看起来是 AI 在提速，实际上 token 花了不少，人还要反复兜底。

这篇文章想整理一种更稳的做法：把 OpenSpec 和 Superpowers 组合起来。OpenSpec 负责把需求变成结构化的设计产物，Superpowers 负责约束 AI 的工作纪律。两者合在一起，本质上是在 AI 和代码之间加了一层“流程护栏”。

为什么不是只用一个工具

OpenSpec 和 Superpowers 看起来有不少重叠：它们都会涉及需求分析、设计、任务拆解、执行和检查。但如果拆开看，两者的优势并不一样。

OpenSpec 更像一个规范驱动开发框架。它擅长把一段需求拆成几个明确的 Markdown 产物：

也就是说，OpenSpec 的强项是让 AI 先把“需求意图”落到纸面上。它帮我们把模糊的一句话变成可以审查、可以讨论、可以追踪的设计资料。

Superpowers 的侧重点则不同。它更像一套开发纪律：什么时候要先检查技能，什么时候要头脑风暴，什么时候必须先写测试，什么时候要做代码审查，什么时候不能直接相信审查意见。它关心的不是单个设计文档长什么样，而是 AI 在整个开发过程中有没有遵守专业工程流程。

第一，不要把所有 Skill 都接进来。Skill 越多，流程越重，token 消耗也越高。真正有价值的是按项目风险选择关键门禁：设计生成、设计检查、测试约束、增量实现、代码审查。

第二，OpenSpec 的产物要按项目口味改造。比如项目如果强调 DDD，就应该要求 design.md 写清楚领域对象、应用服务、接口调用链路和出入参。如果项目更偏传统三层架构，就不要硬套复杂设计。

第三，实现阶段必须引用设计文档。只看 tasks.md 会让 AI 变成任务执行器，看起来快，但容易丢掉架构约束。

第四，Superpowers 的价值不在于“多问问题”，而在于阻止 AI 在证据不足时继续前进。好的流程应该允许 AI 说“这里还不确定，需要确认”，而不是永远假装能做。

第五，不要把模型选择当成流程本身。模型能力当然重要，但稳定交付更依赖上下文质量、流程约束和验证手段。一个强模型如果没有流程，也可能写得很发散；一个普通模型如果被设计文档和测试约束住，反而能稳定完成边界清楚的任务。

用 AI 辅助写后端代码时，我遇到过一个很典型的问题：如果提示词只写“帮我实现这个接口”或者“帮我写一段 SQL 查出这些数据”，AI 通常能把功能写出来，但它不一定会关心这段 SQL 执行多少次、会不会慢、数据量变大后还能不能扛住。

这次智慧调度需求里，getMonitoring 和 initiateDispatch 两个接口就暴露了这个问题。功能上看，接口能返回泵站监测数据、摄像头编码、预警状态、上游泵站和建议操作；但性能上看，里面隐藏了大量循环查库。局域网环境下可能没感觉，一旦数据库连接切到 VPN 环境，单次查询延迟被放大，接口响应就从“还能接受”变成了接近不可用。

这篇文章不展开所有业务细节，只复盘一个核心教训：让 AI 写 SQL 时，不能只要求功能正确，还要把性能约束写进提示词和验收标准。

一、功能正确不等于工程正确

getMonitoring 是一个运行监测接口。前端传入区域类型，比如泵站 bz，后端要返回该区域下所有泵站的实时数据：

  • 泵站名称、坐标、在线状态；
  • 当前液位、瞬时流量等公共指标；
  • 每台泵机的运行状态、运行模式、电流、电压等指标；
  • 是否预警、预警类型；
  • 摄像头编码和最新数据时间。

initiateDispatch 是发起调度初始化接口。前端传入一个预警泵站终端编号，后端要返回当前泵站、上游泵站以及每台泵机的建议操作。

尤其是涉及数据库字段、接口参数、旧系统表结构时，如果只是把需求文档丢给 AI，让它直接写方案，它很容易根据字段名、业务含义和常见命名习惯补全细节。方案读起来通顺，步骤也像那么回事，但里面可能藏着一个致命前提：这些字段到底存不存在，AI 并没有真的验证过。

三、为什么 AI 容易犯这种错

AI 写研发计划时，很容易出现三类“想当然”。

第一类是字段想当然。看到“起点编号”，就推测字段可能叫 start_code、qi_dian_bia_hao 或类似名字；看到“方向”，就认为表里应该有方向字段。推测不一定错，但推测不能当成事实。

第二类是环境想当然。项目可能有本地开发库、测试库、VPN 环境、生产只读库，甚至同名表在不同环境里结构不同。如果 AI 没有先读取项目配置，而是用旧脚本、旧连接或记忆里的地址去查库，结论就会偏掉。

第三类是核查想当然。很多时候我们说“帮我检查这个设计有没有问题”，AI 会做文本层面的检查：字段命名是否前后一致、逻辑是否顺、接口参数是否完整。但真正的研发核查必须落到证据上：配置从哪里来，SQL 查了什么，结果有多少列，差异在哪里。

面试官问“Skill 里面不是可以有脚本嘛”，其实问到了 Skill 的一个核心价值：把确定性的复杂操作交给脚本，而不是每次都让模型临场发挥。

  • 解析 HTML 中的所有图片来源；

  • 下载远程图片；

  • 把 Markdown 里的远程图片链接替换成本地相对路径。

这些事情让 Agent 每次临时写代码都可以做，但不稳定，也浪费上下文。更好的方式是把它们写成脚本，放进 Skill 目录。

脚本带来的好处有三个。

第一，结果更确定。脚本经过测试后，同样输入更容易得到同样输出。

第二，节省上下文。Agent 不需要把几百行脚本内容全部读进上下文，只需要知道“这个脚本能做什么、参数是什么、运行后看结果”。

第三，便于复用和演进。以后需求变了，比如支持 srcset、支持 data:image、支持 DOCX 图片提取，只要改脚本和测试，不需要每次重新教 Agent。

所以 Skill 里的脚本不是装饰品，而是把“知识说明”变成“可执行工作流”的关键。

大语言模型基础补充：Encoder-only 与 Decoder-only 到底差在哪

发表于 2026-05-28 更新于 2026-06-09 分类于 AI与Agent

上一篇整理大语言模型基础时，我把重点放在了“从语言模型到 Transformer，再到 Decoder-Only 大模型”这条主线上。后来又想到几个更具体的问题：

  1. BERT 这种 Encoder-only 架构和 Llama 这种 Decoder-only 架构到底差在哪里？
  2. 自回归模型在训练和 prefill 时都能并行处理整段序列，因果掩码是如何同时保证计算效率和信息不泄露的？
  3. 既然 Encoder 能双向看上下文，为什么今天通用对话模型反而主要是 Decoder-only？

这些问题很容易混在一起。整理之后，我发现关键不是简单地说“谁更先进”，而是要看它们解决的任务不同。

一、先把几个容易混淆的点放在前面

在展开之前，先把几个概念边界放清楚，否则后面很容易把不同架构混在一起。

第一，BERT 和 Llama 代表的是两条不同路线。BERT 是 Encoder-only 的代表，擅长文本理解和表征；Llama 是 Decoder-only 的代表，擅长自回归生成。但如果细分模型谱系，要注意 RoBERTa 是 Meta 基于 BERT 思路改进的模型，DistilBERT 主要来自 Hugging Face，TinyBERT 来自其他研究团队，它们不能笼统归成 Google 官方版本。

第二，纯自回归模型也叫 CausalLM。它的核心规则是因果掩码：当前位置只能关注自己和之前的位置。这个规则不只在推理生成时存在，在训练、prefill 和 decode 阶段都存在。

第三，Decoder-only 模型能利用完整 prompt，并不等于 prompt 里的每个早期 token 都获得了双向上下文。更准确地说，是生成下一个 token 的最后位置可以条件化整段已经输入的 prompt。

第四，PrefixLM 和 CausalLM 不是一回事。PrefixLM 可以让前缀部分使用类似 Encoder 的双向注意力，再让生成部分使用自回归掩码；但 Llama、Qwen 这类公开资料较多的主流生成模型通常按 CausalLM 来理解，prompt 部分也遵守单向因果掩码。GPT、Claude、Gemini 这类闭源前沿模型不一定公开完整内部结构，但从对话式生成、代码生成和工具调用的外部行为看，也可以先放在“自回归生成范式”下理解。

第五，“Encoder 不火了”这个说法不准确。Encoder 只是退出了通用聊天模型的中心舞台，但在 Embedding、Rerank、分类、NER、检索、视觉编码、多模态表征等任务中依然很常见。

二、Encoder-only：为了理解整段输入

BERT 的核心思路是：如果任务是理解文本，而不是从左到右写文本，那么模型最好能同时看到一个词的左边和右边。

比如“苹果”这个词：

如果模型只能从左往右读，读到“苹果”时还不知道后面是“店”还是别的词，就很难立刻判断含义。Encoder-only 架构不使用 causal mask，因此每个 token 都可以和整句里的所有 token 做 self-attention。经过多层 Transformer Encoder 之后，每个位置的输出向量都包含了全局上下文信息。

BERT 的训练目标是 Masked Language Modeling，也就是完形填空。它会随机选中一部分 token，让模型根据左右上下文预测被遮住的内容。

这带来了一个很直接的优势：Encoder 生成的是高质量的上下文表征。它很适合做这些任务：

  1. 文本分类：判断情感、意图、主题。
  2. 命名实体识别：找出人名、地名、组织名等。
  3. 句子匹配：判断两段文本是否相似、是否蕴含。
  4. 向量表征：把文本编码成 embedding，用于检索或聚类。
  5. Rerank：对召回结果做更精细的相关性排序。

所以 Encoder-only 可以理解为“阅读理解专家”。它不擅长连续开放式生成，但很擅长把输入读透。

四、位置编码不会泄露未来内容

位置编码只告诉模型“这个 token 在第几个位置”，不告诉模型“后面那个位置的内容是什么”。

可以把位置编码理解成座位号：

  1. 没有位置编码时，模型很难区分“我 喜欢 吃 苹果”和“苹果 吃 喜欢 我”。
  2. 有位置编码时，模型知道每个 token 的顺序。
  3. 但如果 causal mask 屏蔽了后面的位置，模型仍然拿不到后面 token 的语义内容。

所以，位置编码解决的是顺序感；因果掩码控制的是信息流方向。两者并不矛盾。

五、prefill 阶段到底发生了什么

这个问题最容易混淆。

假设用户输入：

Decoder-only 模型在 prefill 阶段会一次性处理整段 prompt。这个“一次性”指的是工程上的并行计算，并不代表注意力变成了双向。

在纯正的自回归模型中，因果掩码是 Self-Attention 里的硬性规则。无论是训练、prefill，还是 decode，它都不会消失。也就是说：

  1. 处理“我”时，它只能看到“我”。
  2. 处理“苹果”时，它的隐藏状态只能融合“我”“去”“苹果”这些前文信息。
  3. “苹果”这个位置本身看不到后面的“店”和“手机”。

所以，早期 token 并不会因为整段 prompt 已经输入了，就突然获得双向上下文。它们依然只能看历史。

那模型为什么仍然能翻译对？

因为最终用于预测回答第一个 token 的位置，是 prompt 的末尾位置。这个位置排在整个 prompt 的最后，因此它的 Query 被允许关注前面所有输入 token 的 Key 和 Value。

换句话说，最后位置的隐藏状态像一个漏斗，会汇聚整段 prompt 中已经出现过的信息。它可以同时关注到“苹果”“店”“新手机”“请翻译成英文”这些位置，然后以这个末尾隐藏状态为基础，生成回答的第一个 token。

后续生成出来的每一个新 token，也都会排在序列更靠后的位置，因此它们同样能看到完整 prompt 和此前已经生成的内容。

换句话说：

  1. 早期 token 的表示不是双向的。
  2. 生成答案的当前位置可以看到完整 prompt。
  3. Decoder-only 的“理解整段输入”，主要体现在输出位置对整段历史的条件化上。

这和 Encoder-only 的双向表征不是一回事。Encoder 是每个 token 都能同时看左右上下文；Decoder 是每个位置只能看历史，但当 prompt 已经完整输入后，末尾生成位置的历史已经包含整段 prompt。

这里也可以顺手区分一下 PrefixLM。PrefixLM 会把输入分成“前缀区”和“生成区”：前缀区内部可以使用双向注意力，生成区再使用自回归注意力。因此，PrefixLM 中 prompt 部分确实可能获得类似 Encoder 的全局视野。但 CausalLM 不这样做。在 Llama、GPT、Qwen 这类主流自回归模型里，即使是 prompt 部分，也严格遵守单向因果掩码。

六、为什么通用大模型主要走 Decoder-only

既然 Encoder 能双向看上下文，为什么 ChatGPT、Llama、Qwen、Claude、Gemini 这类通用模型主要表现为自回归生成？

我现在的理解是，原因主要有四个。

第一，生成任务天然匹配自回归。聊天、写作、代码生成、工具调用计划，本质上都可以统一成“基于已有上下文生成下一步”。Decoder-only 的训练目标和使用方式非常一致。

第二，预训练数据利用方式简单。互联网上有海量无标注文本，直接做 next token prediction 就可以训练，不需要人工标注任务标签。

第三，模型规模扩大后，next token prediction 会逼迫模型学习很多隐含结构。为了预测后文，模型需要学习语法、事实、常识、代码模式、推理模板和人类表达习惯。不能说它一定形成了真正的人类式理解，但这个目标确实非常适合规模化。

第四，自回归模型很适合上下文学习。给它几个示例，它可以顺着上下文继续生成符合格式的答案。这让很多任务不必每次都微调模型。当然，“不必每次微调”不等于“微调被淘汰”。在特定领域、稳定格式、高一致性要求的场景里，微调、RAG、工具调用和评估流程仍然很重要。

所以 Decoder-only 不是因为它在所有方面都比 Encoder 更好，而是因为它更适合做一个统一的生成接口。

七、Encoder 现在仍然有价值

Encoder 不是过时了，而是分工变了。

在很多工程系统里，Encoder 仍然很适合承担“理解、编码、排序、对齐”的角色。例如：

  1. 向量检索：用 embedding 模型把文档和查询编码成向量。
  2. 语义排序：用 cross-encoder 或 reranker 精排候选结果。
  3. 分类抽取：对短文本做意图识别、实体识别、风险分类。
  4. 多模态系统：用视觉 encoder 把图像变成可供语言模型使用的特征。
  5. RAG 系统：检索、召回、重排、去重这些环节经常依赖 encoder 或 encoder-like 模型。

如果把 Decoder-only 看成负责“表达和行动”的模型，那么 Encoder 更像负责“读懂和压缩输入”的模型。Agent 系统里，这两类能力经常是一起出现的。

八、模型谱系的简要记法

为了后面复习方便，我把常见模型按架构和生成范式粗略记一下。这里需要先加一个时间戳：本文写于 2026-05-28，前沿模型更新很快，下面只按当时公开资料记录，不把没有公开的内部结构说死。

Encoder-only 代表：

  1. BERT-Base：12 层 Encoder，约 110M 参数。
  2. BERT-Large：24 层 Encoder，约 340M 参数。
  3. mBERT、Chinese BERT：Google 官方多语言和中文版本。
  4. RoBERTa、ALBERT、DistilBERT、TinyBERT：BERT 思路下的改进、压缩或训练策略变化，需要注意它们不都来自 Google。

典型 Decoder-only / CausalLM 代表：

  1. Llama 系列：Meta 的开源权重大模型路线，从 Llama 1 到 Llama 3.x，再到 Llama 4 引入 MoE 和原生多模态。
  2. Qwen、DeepSeek、Mistral 等：许多开源或开放权重的通用生成模型，也主要采用 Decoder-only 或以自回归生成作为核心输出机制。
  3. GPT 系列：公开资料中，GPT-4 是 Transformer-style、next-token prediction 路线。到 GPT-5、GPT-5.5 之后，OpenAI 更强调“统一系统”“reasoning”“agentic coding”“computer use”等产品能力；因此可以把它们按生成式自回归范式理解，但不应在没有官方公开细节时断言完整内部架构。

截至 2026-05-28，几个更新的闭源前沿模型可以这样记：

  1. GPT-5.5 / GPT-5.5 Pro：OpenAI 在 2026-04-23 发布，强调 agentic coding、知识工作、科研分析、工具使用和 Codex 场景。包括我现在使用的 Codex 这类 GPT 系列产品，也可以先按“基于上下文持续生成下一步，并结合工具完成任务”的范式来理解；但具体内部结构仍以官方公开资料为准。
  2. Claude Opus 4.7：Anthropic 在 2026-04-16 发布，定位在复杂软件工程、长程多步骤任务、视觉理解和 Agent 工作流。Claude 的完整内部架构同样不是公开教材级信息，因此博客里更适合写“前沿生成式 / hybrid reasoning 模型”，而不是武断归类成某个纯粹结构。
  3. Gemini 3.1 Pro / Gemini 3.5 Flash：Google 在 2026 年继续推进 Gemini 3 系列，3.1 Pro 面向复杂推理和多模态任务，I/O 2026 又推出 3.5 Flash，强调速度和 agentic workflows。Gemini 从一开始就是多模态模型族，实际系统里通常还会包含视觉、音频、工具和检索等组件。

Llama 系列里有几个节点值得记：

  1. Llama 1：7B、13B、33B、65B，主要面向研究。
  2. Llama 2：7B、13B、70B，加入 Chat 版本和更明确的商用许可。
  3. Llama 3：8B、70B，训练数据和 tokenizer 都有明显升级。
  4. Llama 3.1：8B、70B、405B，上下文窗口提升到 128K，并强化多语言和工具使用能力。
  5. Llama 3.2：加入 1B、3B 轻量文本模型，以及 11B、90B 视觉模型。
  6. Llama 4：Scout 和 Maverick 是 MoE、原生多模态模型；Scout 是 17B active、16 experts、109B total，并支持 10M 级上下文。Maverick 是 17B active、128 experts、400B total。Behemoth 在发布时是预览中的教师模型。

九、最后的理解

这次补充让我对“模型架构”这件事少了一点二选一的执念。

Encoder-only 的核心是双向理解，它把输入压缩成高质量表征。Decoder-only 的核心是自回归生成，它把已有上下文不断延展成新的内容。一个更像阅读理解，一个更像连续写作。

今天通用大模型主要表现为生成式自回归范式，并不代表 Encoder 没价值。真正做应用时，尤其是 Agent 或 RAG 系统，经常需要两者协作：Encoder 负责把资料找准、排好、压缩好，生成模型负责根据上下文推理、生成、调用工具和解释结果。

所以我后续再看 Agent 架构时，会更关注一个问题：系统里的每一步到底是在做“理解与检索”，还是在做“生成与行动”。这个区分，比单纯记住某个模型名字更有用。
