Ollama 本地跑大模型：从硬件评估到 API 和知识库

发表于 2026-06-04 分类于 探索AI-Agents

把大模型接到日常工作里，最直接的方式当然是调用云端 API。但只要用得稍微深入一点，就会遇到几个现实问题：调用要花钱，私有代码和文档不一定方便上传，网络不好时体验也不稳定。

所以，本地跑一个开源大模型很值得尝试。它不一定马上替代线上最强模型，但能解决三件事：离线可用、数据留在本机、成本可控。更重要的是，跑通一次 Ollama 之后，模型、API、知识库、图形客户端这些概念会变得非常具体。

这篇文章讲述了一条实践我的路径：先判断自己的电脑能跑什么模型，再安装 Ollama，下载模型，接入 Python API，最后看看如何扩展到本地知识库和图形界面。

一、先别急着下载模型

很多本地部署失败不是因为命令写错，而是因为模型选大了。模型参数越多，通常能力越强，但也越吃内存、显存和磁盘。电脑带不动时，表现可能是下载后启动失败、生成特别慢，或者系统内存压力很大。

所以第一步建议先做硬件评估。Can I Run AI 可以根据内存、CPU、GPU 等信息筛选适合本机运行的模型：

一个保守的入门判断是：

  1. 8GB 内存：优先尝试 1.5B 或 3B 级别的小模型。
  2. 16GB 内存：可以尝试 7B 级别模型，这是本地体验和硬件压力之间比较均衡的选择。
  3. 有 NVIDIA 独显且显存充足：可以考虑更大的模型，推理速度也会明显好很多。

不要被“最大”“最强”牵着走。本地模型选型更像工程取舍：能稳定跑起来，延迟能接受，输出质量够用，比单纯追排行榜更重要。

十、我建议的学习顺序

如果是第一次本地跑大模型，可以按这个顺序来：

  1. 用 Can I Run AI 或类似工具先看硬件能跑什么。
  2. 安装 Ollama，验证 ollama --version。
  3. 下载一个 3B 小模型，先跑通 ollama run。
  4. 用 Python 调一次本地 API。
  5. 再尝试 7B 模型，比较速度和效果。
  6. 接 Cherry Studio，获得更舒服的聊天界面。
  7. 最后再做本地知识库或 Modelfile 定制。

这样走的好处是每一步都有明确反馈：命令能不能跑、模型能不能答、API 能不能通、知识库能不能基于文档回答。比一次性把所有组件装上去更容易定位问题。

本地大模型的价值，不只是省 API 钱。它更像一个可控的实验环境：你可以看到模型如何被下载、如何被调用、如何和自己的文档结合，也能更直观地理解大模型应用背后的工程结构。

Maven 父 POM 解析失败：一次 IDEA 与终端行为不一致的排查

发表于 2026-06-01 分类于 学习笔记

最近在处理一个老项目的 Maven 构建问题时，遇到了一个比较典型、但排查起来容易绕进去的场景：同一套项目、同一个 Maven 安装目录、同一份 settings.xml，在终端里执行 Maven 命令可以成功，但在 IDEA 的 Maven 面板里点击 clean 却一直失败。

表面上看，这是一个父 POM 解析失败的问题；继续往下查，会发现它同时牵涉到 Maven 本地仓库缓存、公司内部依赖没有发布到远程仓库、IDEA Maven 集成行为差异，以及 parent.relativePath 配置缺失。

第一轮排查：本地仓库里明明有 POM，为什么还报找不到

文件 状态

这里有两个 Maven 本地仓库里很容易被忽略的文件。

.lastUpdated 用来记录某个依赖或 POM 从远程仓库解析失败的结果。Maven 为了避免每次构建都重复请求远程仓库，会把失败状态缓存起来。在更新间隔未到之前，它可能不会重新尝试解析。

_remote.repositories 则记录本地文件来自哪个远程仓库，或者是否是本地安装的文件。如果这个记录和当前构建使用的仓库配置对不上，也可能导致 Maven 认为当前文件不可用。

所以第一轮判断是：虽然 zzht-component-2.3.0.pom 已经被手动放进了本地仓库，但 Maven 仍然受到了失败缓存和远程仓库标记的影响。

这说明问题不只在本地仓库缓存上。

第三轮排查：终端 Maven 与 IDEA Maven 的差异

为了排除环境不一致，我继续对比了终端和 IDEA 的 Maven 配置：

但结果还是一样：终端成功，IDEA 失败。

这类现象通常说明 IDEA 内部的 Maven 项目模型构建过程，和命令行 Maven 在某些细节上并不完全一致。尤其是导入项目、解析父 POM、构建 Maven model 时，IDEA 会有自己的集成逻辑。

也就是说，继续围绕本地仓库缓存修修补补，可能只能解决终端构建，不能稳定解决 IDEA 导入和构建。

这时就要回到 POM 本身，看父 POM 的解析路径是否合理。

第四，也是最根本的一点：项目没有通过 relativePath 明确告诉 Maven 父 POM 的本地位置，而是把解析压力全部交给仓库。

重新理解 Agent Skill：它不只是一个 Markdown 文件

发表于 2026-05-31 分类于 探索AI-Agents

前段时间面试时，我被问到一个问题：Skill 到底是什么？

我当时的第一反应是：Skill 不就是一个 SKILL.md 文件吗？这个回答不能说完全错，但明显太窄了。面试官接着追问：Skill 里面不是还可以有脚本吗？

这个追问一下子暴露了我当时理解里的盲区。我把 Skill 的入口文件当成了 Skill 的全部，却没有把它看成一个完整的能力包。后来我又读了一些关于 MCP、Tools、Skills 的材料，并自己动手做了一个 MarkItDown 转 Markdown 的工作流，才慢慢把这几件事串起来。

这篇文章就围绕这个问题展开：Skill 不是单纯的 Markdown 文件，而是一种让 Agent 按需加载知识、流程、脚本和资源的组织方式。

二、Skill、MCP 和 Tools 分别解决什么问题

理解 Skill 时，很容易把它和 MCP、Tools 混在一起。它们都在扩展 Agent 能力，但所在层级不同。

可以先用三个问题区分：

Tools 是最小的执行单元。比如查询数据库、读取文件、调用浏览器、转换文档，本质上都可以包装成一个 Tool。Tool 通常有明确的输入输出 schema，执行结果也比较确定。

MCP 是连接层。它定义了一套协议，让不同 Agent 应用可以用统一方式发现和调用外部工具。没有 MCP 时，每个 Agent 应用都要分别对接每个工具；有了 MCP，工具可以通过标准协议暴露出来，Agent 客户端按协议调用。

Skill 则更偏知识层和流程层。它不一定直接提供一个外部接口，而是告诉 Agent：面对某类任务时，应该怎样判断、怎样拆解、怎样调用现有工具、什么时候运行脚本、什么时候提醒用户风险。

四、为什么 Skill 里要放脚本

面试官问“Skill 里面不是可以有脚本嘛”，其实问到了 Skill 的一个核心价值：把确定性的复杂操作交给脚本，而不是每次都让模型临场发挥。

模型很擅长理解意图、做判断、写说明，但它并不适合把一堆细节操作都放在上下文里一步步手搓。比如：

  • 解析 HTML 中的所有图片来源；
  • 处理相对路径、根路径、协议相对路径；
  • 下载远程图片；
  • 判断 Content-Type 推断扩展名；
  • 避免文件名冲突；
  • 把 Markdown 里的远程图片链接替换成本地相对路径。

这些事情让 Agent 每次临时写代码都可以做，但不稳定，也浪费上下文。更好的方式是把它们写成脚本，放进 Skill 目录。

脚本带来的好处有三个。

第一，结果更确定。脚本经过测试后，同样输入更容易得到同样输出。

第二，节省上下文。Agent 不需要把几百行脚本内容全部读进上下文，只需要知道“这个脚本能做什么、参数是什么、运行后看结果”。

第三，便于复用和演进。以后需求变了，比如支持 srcset、支持 data:image、支持 DOCX 图片提取，只要改脚本和测试，不需要每次重新教 Agent。

所以 Skill 里的脚本不是装饰品，而是把“知识说明”变成“可执行工作流”的关键。

大语言模型基础补充：Encoder-only 与 Decoder-only 到底差在哪

发表于 2026-05-28 分类于 探索AI-Agents

上一篇整理大语言模型基础时，我把重点放在了“从语言模型到 Transformer，再到 Decoder-Only 大模型”这条主线上。后来又想到几个更具体的问题：

  1. BERT 这种 Encoder-only 架构和 Llama 这种 Decoder-only 架构到底差在哪里？
  2. 自回归模型在训练和 prefill 时都能并行处理整段序列，因果掩码是如何同时保证计算效率和信息不泄露的？
  3. 既然 Encoder 能双向看上下文，为什么今天通用对话模型反而主要是 Decoder-only？

这些问题很容易混在一起。整理之后，我发现关键不是简单地说“谁更先进”，而是要看它们解决的任务不同。

一、先把几个容易混淆的点放在前面

在展开之前，先把几个概念边界放清楚，否则后面很容易把不同架构混在一起。

第一，BERT 和 Llama 代表的是两条不同路线。BERT 是 Encoder-only 的代表，擅长文本理解和表征；Llama 是 Decoder-only 的代表，擅长自回归生成。但如果细分模型谱系，要注意 RoBERTa 是 Meta 基于 BERT 思路改进的模型，DistilBERT 主要来自 Hugging Face，TinyBERT 来自其他研究团队，它们不能笼统归成 Google 官方版本。

第二，纯自回归模型也叫 CausalLM。它的核心规则是因果掩码：当前位置只能关注自己和之前的位置。这个规则不只在推理生成时存在，在训练、prefill 和 decode 阶段都存在。

第三，Decoder-only 模型能利用完整 prompt，并不等于 prompt 里的每个早期 token 都获得了双向上下文。更准确地说，是生成下一个 token 的最后位置可以条件化整段已经输入的 prompt。

第四，PrefixLM 和 CausalLM 不是一回事。PrefixLM 可以让前缀部分使用类似 Encoder 的双向注意力，再让生成部分使用自回归掩码；但 Llama、Qwen 这类公开资料较多的主流生成模型通常按 CausalLM 来理解，prompt 部分也遵守单向因果掩码。GPT、Claude、Gemini 这类闭源前沿模型不一定公开完整内部结构，但从对话式生成、代码生成和工具调用的外部行为看，也可以先放在“自回归生成范式”下理解。

第五，“Encoder 不火了”这个说法不准确。Encoder 只是退出了通用聊天模型的中心舞台，但在 Embedding、Rerank、分类、NER、检索、视觉编码、多模态表征等任务中依然很常见。

二、Encoder-only：为了理解整段输入

BERT 的核心思路是：如果任务是理解文本，而不是从左到右写文本，那么模型最好能同时看到一个词的左边和右边。

比如“苹果”这个词：

如果模型只能从左往右读，读到“苹果”时还不知道后面是“店”还是别的词，就很难立刻判断含义。Encoder-only 架构不使用 causal mask，因此每个 token 都可以和整句里的所有 token 做 self-attention。经过多层 Transformer Encoder 之后，每个位置的输出向量都包含了全局上下文信息。

BERT 的训练目标是 Masked Language Modeling，也就是完形填空。它会随机选中一部分 token，让模型根据左右上下文预测被遮住的内容。

这带来了一个很直接的优势：Encoder 生成的是高质量的上下文表征。它很适合做这些任务：

  1. 文本分类：判断情感、意图、主题。
  2. 命名实体识别：找出人名、地名、组织名等。
  3. 句子匹配：判断两段文本是否相似、是否蕴含。
  4. 向量表征：把文本编码成 embedding，用于检索或聚类。
  5. Rerank：对召回结果做更精细的相关性排序。

所以 Encoder-only 可以理解为“阅读理解专家”。它不擅长连续开放式生成，但很擅长把输入读透。

四、位置编码不会泄露未来内容

位置编码只告诉模型“这个 token 在第几个位置”，不告诉模型“后面那个位置的内容是什么”。

可以把位置编码理解成座位号：

  1. 没有位置编码时，模型很难区分“我 喜欢 吃 苹果”和“苹果 吃 喜欢 我”。
  2. 有位置编码时，模型知道每个 token 的顺序。
  3. 但如果 causal mask 屏蔽了后面的位置，模型仍然拿不到后面 token 的语义内容。

所以，位置编码解决的是顺序感；因果掩码控制的是信息流方向。两者并不矛盾。

五、prefill 阶段到底发生了什么

这个问题最容易混淆。

假设用户输入：

Decoder-only 模型在 prefill 阶段会一次性处理整段 prompt。这个“一次性”指的是工程上的并行计算，并不代表注意力变成了双向。

在纯正的自回归模型中，因果掩码是 Self-Attention 里的硬性规则。无论是训练、prefill，还是 decode，它都不会消失。也就是说：

  1. 处理“我”时，它只能看到“我”。
  2. 处理“苹果”时，它的隐藏状态只能融合“我”“去”“苹果”这些前文信息。
  3. “苹果”这个位置本身看不到后面的“店”和“手机”。

所以，早期 token 并不会因为整段 prompt 已经输入了，就突然获得双向上下文。它们依然只能看历史。

那模型为什么仍然能翻译对？

因为最终用于预测回答第一个 token 的位置，是 prompt 的末尾位置。这个位置排在整个 prompt 的最后，因此它的 Query 被允许关注前面所有输入 token 的 Key 和 Value。

换句话说，最后位置的隐藏状态像一个漏斗，会汇聚整段 prompt 中已经出现过的信息。它可以同时关注到“苹果”“店”“新手机”“请翻译成英文”这些位置，然后以这个末尾隐藏状态为基础，生成回答的第一个 token。

后续生成出来的每一个新 token，也都会排在序列更靠后的位置，因此它们同样能看到完整 prompt 和此前已经生成的内容。

换句话说：

  1. 早期 token 的表示不是双向的。
  2. 生成答案的当前位置可以看到完整 prompt。
  3. Decoder-only 的“理解整段输入”，主要体现在输出位置对整段历史的条件化上。

这和 Encoder-only 的双向表征不是一回事。Encoder 是每个 token 都能同时看左右上下文；Decoder 是每个位置只能看历史，但当 prompt 已经完整输入后，末尾生成位置的历史已经包含整段 prompt。

这里也可以顺手区分一下 PrefixLM。PrefixLM 会把输入分成“前缀区”和“生成区”：前缀区内部可以使用双向注意力，生成区再使用自回归注意力。因此，PrefixLM 中 prompt 部分确实可能获得类似 Encoder 的全局视野。但 CausalLM 不这样做。在 Llama、GPT、Qwen 这类主流自回归模型里，即使是 prompt 部分，也严格遵守单向因果掩码。

六、为什么通用大模型主要走 Decoder-only

既然 Encoder 能双向看上下文，为什么 ChatGPT、Llama、Qwen、Claude、Gemini 这类通用模型主要表现为自回归生成？

我现在的理解是，原因主要有四个。

第一，生成任务天然匹配自回归。聊天、写作、代码生成、工具调用计划，本质上都可以统一成“基于已有上下文生成下一步”。Decoder-only 的训练目标和使用方式非常一致。

第二，预训练数据利用方式简单。互联网上有海量无标注文本，直接做 next token prediction 就可以训练，不需要人工标注任务标签。

第三，模型规模扩大后，next token prediction 会逼迫模型学习很多隐含结构。为了预测后文，模型需要学习语法、事实、常识、代码模式、推理模板和人类表达习惯。不能说它一定形成了真正的人类式理解，但这个目标确实非常适合规模化。

第四，自回归模型很适合上下文学习。给它几个示例，它可以顺着上下文继续生成符合格式的答案。这让很多任务不必每次都微调模型。当然，“不必每次微调”不等于“微调被淘汰”。在特定领域、稳定格式、高一致性要求的场景里，微调、RAG、工具调用和评估流程仍然很重要。

所以 Decoder-only 不是因为它在所有方面都比 Encoder 更好，而是因为它更适合做一个统一的生成接口。

七、Encoder 现在仍然有价值

Encoder 不是过时了，而是分工变了。

在很多工程系统里，Encoder 仍然很适合承担“理解、编码、排序、对齐”的角色。例如：

  1. 向量检索：用 embedding 模型把文档和查询编码成向量。
  2. 语义排序：用 cross-encoder 或 reranker 精排候选结果。
  3. 分类抽取：对短文本做意图识别、实体识别、风险分类。
  4. 多模态系统：用视觉 encoder 把图像变成可供语言模型使用的特征。
  5. RAG 系统：检索、召回、重排、去重这些环节经常依赖 encoder 或 encoder-like 模型。

如果把 Decoder-only 看成负责“表达和行动”的模型，那么 Encoder 更像负责“读懂和压缩输入”的模型。Agent 系统里，这两类能力经常是一起出现的。

  4. RoBERTa、ALBERT、DistilBERT、TinyBERT：BERT 思路下的改进、压缩或训练策略变化，需要注意它们不都来自 Google。

典型 Decoder-only / CausalLM 代表：

  1. Llama 系列：Meta 的开源权重大模型路线，从 Llama 1 到 Llama 3.x，再到 Llama 4 引入 MoE 和原生多模态。
  2. Qwen、DeepSeek、Mistral 等：许多开源或开放权重的通用生成模型，也主要采用 Decoder-only 或以自回归生成作为核心输出机制。
  3. GPT 系列：公开资料中，GPT-4 是 Transformer-style、next-token prediction 路线。到 GPT-5、GPT-5.5 之后，OpenAI 更强调“统一系统”“reasoning”“agentic coding”“computer use”等产品能力；因此可以把它们按生成式自回归范式理解，但不应在没有官方公开细节时断言完整内部架构。

截至 2026-05-28，几个更新的闭源前沿模型可以这样记：

  1. GPT-5.5 / GPT-5.5 Pro：OpenAI 在 2026-04-23 发布，强调 agentic coding、知识工作、科研分析、工具使用和 Codex 场景。包括我现在使用的 Codex 这类 GPT 系列产品，也可以先按“基于上下文持续生成下一步，并结合工具完成任务”的范式来理解；但具体内部结构仍以官方公开资料为准。
  2. Claude Opus 4.7：Anthropic 在 2026-04-16 发布，定位在复杂软件工程、长程多步骤任务、视觉理解和 Agent 工作流。Claude 的完整内部架构同样不是公开教材级信息，因此博客里更适合写“前沿生成式 / hybrid reasoning 模型”，而不是武断归类成某个纯粹结构。
  3. Gemini 3.1 Pro / Gemini 3.5 Flash：Google 在 2026 年继续推进 Gemini 3 系列，3.1 Pro 面向复杂推理和多模态任务，I/O 2026 又推出 3.5 Flash，强调速度和 agentic workflows。Gemini 从一开始就是多模态模型族，实际系统里通常还会包含视觉、音频、工具和检索等组件。

Llama 系列里有几个节点值得记：

  1. Llama 1：7B、13B、33B、65B，主要面向研究。
  2. Llama 2：7B、13B、70B，加入 Chat 版本和更明确的商用许可。
  3. Llama 3：8B、70B，训练数据和 tokenizer 都有明显升级。
  4. Llama 3.1：8B、70B、405B，上下文窗口提升到 128K，并强化多语言和工具使用能力。
  5. Llama 3.2：加入 1B、3B 轻量文本模型，以及 11B、90B 视觉模型。
  6. Llama 4：Scout 和 Maverick 是 MoE、原生多模态模型；Scout 是 17B active、16 experts、109B total，并支持 10M 级上下文。Maverick 是 17B active、128 experts、400B total。Behemoth 在发布时是预览中的教师模型。

九、最后的理解

这次补充让我对“模型架构”这件事少了一点二选一的执念。

Encoder-only 的核心是双向理解，它把输入压缩成高质量表征。Decoder-only 的核心是自回归生成，它把已有上下文不断延展成新的内容。一个更像阅读理解，一个更像连续写作。

今天通用大模型主要表现为生成式自回归范式，并不代表 Encoder 没价值。真正做应用时，尤其是 Agent 或 RAG 系统，经常需要两者协作：Encoder 负责把资料找准、排好、压缩好，生成模型负责根据上下文推理、生成、调用工具和解释结果。

所以我后续再看 Agent 架构时，会更关注一个问题：系统里的每一步到底是在做“理解与检索”，还是在做“生成与行动”。这个区分，比单纯记住某个模型名字更有用。

大语言模型基础学习笔记：从预测下一个词到构建可靠应用

发表于 2026-05-28 分类于 探索AI-Agents

最近在补大语言模型的基础知识。刚开始看这类材料时，我很容易被一堆名词淹没：N-gram、RNN、LSTM、Transformer、Tokenizer、Scaling Laws、幻觉、RAG。它们看起来像是分散的技术点，但如果顺着一条主线看，其实会清楚很多。

这条主线就是：语言模型本质上是在根据已有上下文预测下一个词元。模型能力的演进，基本都围绕“怎样更好地理解上下文、怎样更高效地学习语言规律、怎样更可靠地生成结果”展开。

一、先理解语言模型在做什么

语言模型的核心任务，是计算一个词序列出现的概率。换句话说，它要判断一句话在语言上是否自然，也要能根据前文推测后面最可能出现的内容。

例如 Bigram 只看前一个词，Trigram 只看前两个词。它的好处是简单、可解释，坏处也很明显：

  1. 数据稀疏。没见过的词组概率容易被估成 0。
  2. 泛化能力差。模型不知道 agent 和 robot 在语义上可能相近。
  3. 上下文太短。窗口之外的信息会被直接丢掉。

所以，语言模型需要从“数词频”走向“学表示”。

二、词嵌入：把离散的词放进连续空间

但早期神经网络语言模型仍然有一个问题：上下文窗口通常是固定的。它比 N-gram 更会泛化，却还是不能很好地处理很长的依赖关系。

三、RNN 与 LSTM：给模型加上记忆

循环神经网络 RNN 的思路很自然：既然语言是一个序列，那模型就按顺序读，每读一个词就更新一次隐藏状态。这个隐藏状态可以理解成模型的短期记忆。

图 3：RNN 通过隐藏状态在序列中传递信息。

RNN 比固定窗口模型更灵活，因为它理论上可以把前面的信息一路传到后面。但实际训练时，它会遇到长期依赖问题。序列越长，反向传播路径越长，梯度就越容易消失或爆炸。结果是，模型很难真正记住很早之前的信息。

LSTM 在 RNN 的基础上引入了细胞状态和门控机制。遗忘门决定丢掉什么，输入门决定写入什么，输出门决定暴露什么。这样一来，信息可以更稳定地在长序列里流动。

不过，RNN 和 LSTM 都有一个绕不开的瓶颈：它们必须按顺序处理序列。第 t 步依赖第 t-1 步，天然不适合大规模并行训练。这也就引出了 Transformer。

四、Transformer：用注意力替代循环

Transformer 的关键变化，是抛弃循环结构，改用注意力机制来建模词元之间的关系。这样模型可以一次性看到整个序列，并并行计算不同位置之间的关联。

最初的 Transformer 采用 Encoder-Decoder 架构，常见于机器翻译这类任务。

图 4：Transformer 由编码器和解码器组成。

可以把它理解成两个角色：

  1. 编码器负责理解输入，把每个词元变成带上下文信息的表示。
  2. 解码器负责生成输出，根据已经生成的内容和编码器结果预测下一个词元。

真正让 Transformer 强大的，是自注意力机制。

五、自注意力：让每个词主动寻找上下文

阅读一句话时，我们不会孤立地看每个词。例如看到 “The agent learns because it is intelligent” 里的 it，我们会自然回看前面的 agent。自注意力就是把这种“回看上下文”的过程数学化。

每个词元会被映射成三个向量：

  1. Query：当前词要查询什么。
  2. Key：其他词能提供什么索引。
  3. Value：其他词实际携带什么信息。

自注意力的计算可以简化成四步：

  1. 用当前词的 Query 和所有词的 Key 计算相关性。
  2. 对相关性分数做缩放，避免数值过大。
  3. 用 Softmax 得到注意力权重。
  4. 用这些权重对 Value 加权求和，得到当前词的新表示。

  1. 位置编码：自注意力本身不知道顺序，所以需要额外注入位置信息。
  2. 前馈网络：对每个位置的表示继续做非线性变换，提取更高阶特征。
  3. 残差连接：让深层网络里的梯度更容易传递。
  4. 层归一化：稳定每一层的输入分布，提升训练稳定性。

这些模块组合起来，才构成了现代大模型的基础骨架。

六、为什么很多大模型是 Decoder-Only

今天常见的生成式模型，大多可以按 Decoder-Only / CausalLM 的思路来理解。以 Llama、Qwen 这类公开资料较多的模型为例，它们的核心目标就是预测下一个词元。GPT 系列、Claude、Gemini 这类闭源前沿模型通常不会完整公开内部架构，但从对话、代码生成、工具调用等使用方式看，也都属于“基于已有上下文持续生成下一步”的生成式范式。

这个过程也叫自回归生成：

  1. 用户给出一段输入。
  2. 模型预测下一个最可能的词元。
  3. 把刚生成的词元接回上下文。
  4. 重复预测，直到生成完整回答或触发停止条件。

这里有个关键细节：模型训练时不能偷看未来答案。所以 Decoder-Only 会使用掩码自注意力，把当前位置之后的词元遮住。这样模型在预测第 t 个词元时，只能依赖第 t 个词元之前的信息。

Decoder-Only 架构简单、目标统一、容易扩展，也天然适合对话、写作、代码生成等任务。这也是它能成为通用大语言模型主流路线的重要原因。

七、和大模型交互：Prompt 与采样参数

理解模型结构之后，再看 Prompt 会更容易。提示词不是魔法，它本质上是在给模型提供上下文、任务边界和输出格式。

常见提示方式可以按示例数量分成三类：

  1. 零样本提示：只给任务，不给示例。
  2. 单样本提示：给一个输入输出示例，让模型模仿格式。
  3. 少样本提示：给多个示例，让模型理解边界和风格。

指令调优之后，模型更擅长理解自然语言命令，所以我们可以直接写“请总结下面的内容”或者“请用 JSON 输出结果”。但在复杂任务里，示例依然很有用，尤其是格式抽取、分类、风格迁移这类场景。

采样参数决定模型如何从概率分布里选择下一个词元：

  1. Temperature 控制随机性。低温度更稳定，高温度更发散。
  2. Top-k 只保留概率最高的 k 个候选词元。
  3. Top-p 保留累计概率达到 p 的最小候选集合。

我的理解是：事实问答、代码生成、数据处理这类任务更适合低温度；头脑风暴、创意写作可以适当提高温度。Top-k 和 Top-p 通常不必同时调得很复杂，先从一个参数开始更容易观察效果。

对于需要推理的问题，思维链提示也很常见。它的核心不是让模型“装作聪明”，而是让模型把中间步骤显式展开，方便我们检查它在哪一步出错。

八、Tokenizer：看不见但很重要的一层

模型不能直接处理自然语言，它实际处理的是 Token ID。分词器负责把文本切成词元，再映射成数字。

最直观的分词方式有两种：

  1. 按词切分：语义直观，但词表会非常大，也容易遇到未登录词。
  2. 按字符切分：词表很小，但单个字符语义太弱，序列会变长。

现代大模型普遍使用子词分词，在词和字符之间折中。常见词可以保留为完整词元，低频词可以拆成多个子词片段。

BPE 是一种典型算法。它从字符级词表开始，每次合并出现频率最高的相邻片段，直到词表达到目标大小。

图 6：BPE 通过不断合并高频片段构建词表。

Tokenizer 对开发者很重要，原因有三个：

  1. 上下文窗口按 Token 计算，不按汉字数、字符数或单词数计算。
  2. API 成本通常和输入输出 Token 数直接相关。
  3. 分词结果会影响模型表现。同一段文本，多一个空格、大小写变化、符号变化，都可能切成不同的 Token 序列。

所以写 Prompt 时，除了语义清楚，也要尽量保持格式稳定。

十、模型选型不要只看“最强”

模型选型不是排行榜第一名就一定最好。实际项目里更常见的是在多个因素之间取舍：

  1. 能力：推理、代码、中文、多模态、长文本，各模型侧重点不同。
  2. 成本：闭源 API 按 Token 计费，开源部署则消耗硬件和运维成本。
  3. 延迟：实时交互场景对响应速度非常敏感。
  4. 上下文窗口：长文档、代码库分析、长期对话都依赖更大的上下文。
  5. 部署方式：API 简单，本地部署更可控。
  6. 生态：工具链、社区、微调方案和部署框架会影响开发效率。
  7. 安全性：面向真实用户时，需要考虑幻觉、偏见、越权调用和敏感信息泄露。

所以我更愿意把模型选型看成工程问题，而不是单纯的模型能力竞赛。先明确任务，再确定约束，最后才是比较模型。

十一、缩放法则与模型局限

大语言模型能力提升的背后，有一个重要经验规律：模型参数量、训练数据量和计算量增加时，模型损失通常会按可预测的趋势下降。这就是缩放法则。

但后来的研究也提醒我们，不能只堆参数。给定计算预算时，模型大小和训练数据量需要匹配。一个参数更少、数据更充分的模型，可能比一个更大但训练不足的模型表现更好。

模型变大后，还会出现一些小模型不明显的能力，比如更好的指令遵循、多步推理、代码生成和链式思考。但这并不意味着模型真正“无所不知”。它仍然有明显局限：

  1. 幻觉：模型可能编造事实，并且表达得很自信。
  2. 知识时效性：模型不知道训练数据之后发生的新事实。
  3. 偏见：训练数据里的社会偏见可能被模型学习并放大。
  4. 推理不稳定：复杂任务中，中间一步出错会影响最终答案。

从应用角度看，缓解这些问题不能只靠“写一个更好的 Prompt”。更可靠的做法是给模型接入外部知识和工具，比如 RAG、搜索、计算器、代码执行器、数据库查询和人工审核流程。

十二、这次学习后的理解

读完这部分内容后，我对大语言模型的理解从“会聊天的黑盒”变得更具体了。

从 N-gram 到词嵌入，是从统计计数走向语义表示；从 RNN 到 Transformer，是从顺序记忆走向并行注意力；从 Encoder-Decoder 到 Decoder-Only，是把生成任务统一成预测下一个词元；从 Prompt 到 Tokenizer，是理解我们如何把任务交给模型；从缩放法则到幻觉问题，则提醒我模型越强，工程约束和验证机制越重要。

如果后续要继续学习智能体，这些基础会很有用。因为 Agent 的规划、记忆、工具调用和结果校验，最后都绕不开这些问题：模型看到了什么上下文，如何生成下一步，什么时候会不可靠，以及我们该如何把它放进一个更稳的系统里。

千万级数据同步到 Elasticsearch：线程池、CountDownLatch 与背压控制

发表于 2026-05-25 分类于 学习笔记

项目上线前，经常会遇到一个典型场景：业务数据已经在 MySQL 里沉淀了一段时间，现在需要一次性同步到 Elasticsearch 索引库中，方便后续做搜索和查询。

如果数据量只有几万条，直接分页同步问题不大。但当数据量来到千万级，比如 1000 万条时，就不能简单地执行一次 SELECT * 把数据全部查出来。这样很容易让 Java 应用端内存被打爆，出现 OOM；同时长时间的大查询也会占住数据库连接，拖慢甚至影响线上数据库。

比较稳妥的思路是：把大任务拆成很多小批次，再通过线程池并发处理，同时用 CountDownLatch 等待所有批次结束。真正关键的地方不只是“用了多线程”，而是要用有界队列和 CallerRunsPolicy 做背压，让同步速度始终被控制在数据库、应用和 ES 都能承受的范围内。

一、核心思路：分批读取，并发写入

千万级数据同步的核心是“分而治之”。

这个过程会带来一个天然的时间差：

  1. 主线程执行 executor.execute(task)。
  2. 线程池发现队列已满，触发 CallerRunsPolicy。
  3. 主线程同步执行 task.run()，开始查 MySQL、转换数据、写 ES。
  4. 在主线程执行任务的这段时间里，它无法继续提交新任务。
  5. 线程池里的工作线程仍然在消费队列中的任务。
  6. 主线程执行完当前任务后，executor.execute(task) 返回，继续进入下一轮 for 循环。

所以主线程不需要额外的通知机制。它执行完 run() 后，代码自然回到原来的循环位置，继续提交下一个任务。

这就是背压：当 ES 写入变慢、数据库查询变慢、工作线程消费不过来时，主线程提交任务的速度也会自动变慢。

还有一个细节：即使任务是主线程执行的，也会进入同一段 Runnable 代码，所以 finally 里的 latch.countDown() 同样会执行。只要 countDown() 放在 finally 里，就能避免某个批次异常后主线程一直等待。

2. 失败批次要能补偿

同步 2000 个批次时，只要有几个批次因为网络抖动、ES 瞬时拒绝写入或数据库超时失败，就可能造成索引数据缺失。

所以 catch 里不能只打印日志。更稳妥的方式是把失败批次记录下来，例如写入失败表、Redis 或本地补偿文件，主流程结束后再进行二次重试。

同时，写 ES 时最好保证幂等。比如使用数据库主键作为 ES 文档 _id，重复写入同一条数据时只是覆盖更新，而不是生成重复文档。

3. Bulk 大小要压测

每批 5000 条只是一个经验值，不是固定答案。

如果单条文档很大，5000 条可能会让单次 Bulk 请求过重，导致 ES 写入慢或者请求体过大。如果单条文档很小，批次太小又会导致网络请求过多，吞吐上不去。

实际落地时要观察几个指标：

  1. 单次 Bulk 请求耗时。
  2. ES 是否出现拒绝写入。
  3. JVM 堆内存和 GC 情况。
  4. MySQL 查询耗时和连接池占用。

然后再调整 pageSize、线程数和队列长度。

4. 数据库压力可能成为瓶颈

线程池开到 CPU * 2 并不代表一定合适。它只是一个起点。

如果压测发现 MySQL CPU 飙高、慢查询增多，或者连接池被打满，就要降低并发线程数，或者增大单批次大小，减少并发查询次数。同步任务的目标不是让应用跑满，而是让数据库、应用和 ES 形成稳定吞吐。

八、总结

千万级数据同步到 Elasticsearch，重点不是简单地“开多线程”，而是建立一个可控的同步流水线。

CountDownLatch 解决的是主线程如何等待所有批次结束；ThreadPoolExecutor 解决的是并发执行；有界队列和 CallerRunsPolicy 解决的是生产速度过快时如何自动减速。

一套比较完整的方案应该同时考虑：

  1. 分批读取，避免一次性加载导致 OOM。
  2. 有界线程池，限制并发和任务积压。
  3. CallerRunsPolicy，在消费变慢时形成背压。
  4. CountDownLatch，等待所有批次完成，并设置超时。
  5. ID 滚动分页，避免 MySQL 深分页问题。
  6. 失败批次记录和重试，保证最终数据完整。
  7. 使用数据库主键作为 ES _id，保证重复写入时具备幂等性。

这样设计后，整个同步任务就不再是一次不可控的大查询，而是一批批可观察、可限流、可补偿的小任务。

分布式路由追踪：从 TraceId 到跨线程透传

发表于 2026-05-23 分类于 学习笔记

在排查线上问题时，最怕看到的是一串散落在不同机器、不同服务、不同线程里的日志：每一条看起来都和问题有关，但又很难串成一条完整的请求链路。

分布式路由追踪要解决的就是这件事：给一次请求一个全局唯一的 TraceId，让它在网关、业务服务、RPC 调用、消息队列、异步线程之间一直传下去。这样排查问题时，就可以根据一个 TraceId 找到完整路径，再结合每个关键步骤的耗时和调用关系定位问题。

一、为什么需要 TraceId

在单体项目里，请求通常只落在某一台机器上的某个进程里。只要日志里能打印出请求标识，基本就可以顺着日志找到整个执行过程。

但在微服务环境下，一次请求可能会经过：

  1. 网关。
  2. A 服务。
  3. B 服务。
  4. MQ 消费者。
  5. 线程池里的异步任务。

如果没有统一的追踪标识，这些日志就会分散在不同服务、不同机器甚至不同线程中。排查问题时只能到处搜索，效率很低。

所以，最基础的做法是引入 TraceId。它代表一次完整请求。只要所有服务都把同一个 TraceId 打进日志，就能把散落的日志重新串起来。

不过，只有 TraceId 还不够。它可以告诉我们“这些日志属于同一次请求”，但不一定能告诉我们“服务之间是如何调用的”。这时还需要 SpanId。

二、TraceId 和 SpanId 分别做什么

可以这样理解：

  • TraceId：标识一整条请求链路。
  • SpanId：标识链路中的某一次调用或某一个执行片段。

比如一次请求从网关进入 A 服务，A 服务再调用 B 服务，B 服务又调用 C 服务。它们拥有同一个 TraceId，但每一次调用都应该有不同的 SpanId。

三、先从单体场景做日志增强

在单体或集群部署的场景里，首先要解决的是“如何无侵入地打印追踪日志”。

需求通常有两个：

  1. 对业务代码尽量无侵入。
  2. 对接口性能影响尽量小。

无侵入可以通过切面编程实现。切面可以分成两类：

  • 静态代理：典型代表是 AspectJ，在编译期完成切面代码注入。
  • 动态代理：典型代表是 Spring AOP，在运行期生成代理对象，再通过代理和反射完成增强。

如果只是做日志记录、限流、耗时统计这类通用增强，静态代理对运行时性能影响更小。动态代理虽然更灵活，但运行期生成代理类和反射调用会带来一定开销。

四、微服务场景：让 TraceId 在服务之间传递

进入微服务后，问题变成了：一次请求跨越多个服务，TraceId 怎么传下去？

基本流程是：

  1. 网关收到外部请求时生成全局唯一的 TraceId。
  2. 网关把 TraceId 放入请求 Header。
  3. 业务服务的 Filter 拦截请求，从 Header 里解析 TraceId。
  4. 服务把 TraceId 放入当前线程的 RequestContext。
  5. 后续 RPC、MQ、异步任务继续从 RequestContext 中读取并透传。

RequestContext 通常基于 ThreadLocal 实现。这样当前请求线程里的业务代码都可以方便地获取 TraceId，而不需要在每个方法参数里显式传递。

在服务之间传递时，常见场景有两类：RPC 调用和消息队列。

九、一次完整链路可以这样串起来

把上面的内容合在一起，一次请求的追踪流程大概是：

  1. 请求进入网关，网关生成 TraceId。
  2. 网关把 TraceId 写入 Header，转发给业务服务。
  3. 业务服务 Filter 解析 Header，写入 RequestContext。
  4. 方法切面记录接口耗时、成功状态和异常信息。
  5. Dubbo 调用前把 TraceId 写入 attachment。
  6. Dubbo 服务提供方从 attachment 中恢复 TraceId。
  7. MQ 发送和消费时通过消息属性继续传递 TraceId。
  8. 线程池任务通过 TaskDecorator 复制上下文。
  9. 特殊异步任务使用 RunnableWrapper 或 CallableWrapper 手动透传。
  10. 日志统一进入 MQ 和 ES，排查时按 TraceId 检索。

这条链路里最重要的不是某一段代码，而是两个动作：入口处生成，边界处透传。

入口包括网关、MQ 消费入口、定时任务入口等。边界包括 RPC、MQ、线程池、手动创建线程等。只要每个边界都处理好，TraceId 就不会轻易断。

十、总结

分布式路由追踪的核心目标，是让一次请求在复杂系统里仍然保持“可观察”。

在实现上，可以分层推进：

  1. 用 AOP 记录方法耗时和执行结果，降低业务侵入。
  2. 用日志采样和集中式检索降低 IO 与排查成本。
  3. 用 TraceId 串联同一次请求的所有日志。
  4. 用 SpanId 补充服务间调用关系。
  5. 用 RPC Filter 和 MQ Header 解决跨服务传递。
  6. 用线程池装饰器和任务包装器解决跨线程传递。

真正容易出问题的地方，往往不是主流程，而是各种边界：服务调用边界、消息边界、线程边界。把这些边界守住，链路追踪才能从“日志里有个 ID”变成真正可用的排查工具。
