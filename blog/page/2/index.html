大语言模型基础学习笔记：从预测下一个词到构建可靠应用

发表于 2026-05-28 更新于 2026-06-09 分类于 AI与Agent

最近在补大语言模型的基础知识。刚开始看这类材料时，我很容易被一堆名词淹没：N-gram、RNN、LSTM、Transformer、Tokenizer、Scaling Laws、幻觉、RAG。它们看起来像是分散的技术点，但如果顺着一条主线看，其实会清楚很多。

这条主线就是：语言模型本质上是在根据已有上下文预测下一个词元。模型能力的演进，基本都围绕“怎样更好地理解上下文、怎样更高效地学习语言规律、怎样更可靠地生成结果”展开。

一、先理解语言模型在做什么

语言模型的核心任务，是计算一个词序列出现的概率。换句话说，它要判断一句话在语言上是否自然，也要能根据前文推测后面最可能出现的内容。

早期的统计语言模型会把一句话拆成多个条件概率相乘。例如，一个句子可以近似看成：

直接计算完整历史几乎不可行，因为上下文组合太多，很多组合在语料里根本没出现过。于是 N-gram 模型引入了马尔可夫假设：预测当前词时，只看前面有限的几个词。

图 1：N-gram 用有限上下文近似完整历史。

例如 Bigram 只看前一个词，Trigram 只看前两个词。它的好处是简单、可解释，坏处也很明显：

  1. 数据稀疏。没见过的词组概率容易被估成 0。
  2. 泛化能力差。模型不知道 agent 和 robot 在语义上可能相近。
  3. 上下文太短。窗口之外的信息会被直接丢掉。

所以，语言模型需要从“数词频”走向“学表示”。

二、词嵌入：把离散的词放进连续空间

神经网络语言模型解决问题的第一步，是把词变成向量。词向量也叫词嵌入，它把每个词映射到一个高维连续空间里。语义相近的词，向量位置也会更接近。

但早期神经网络语言模型仍然有一个问题：上下文窗口通常是固定的。它比 N-gram 更会泛化，却还是不能很好地处理很长的依赖关系。

三、RNN 与 LSTM：给模型加上记忆

循环神经网络 RNN 的思路很自然：既然语言是一个序列，那模型就按顺序读，每读一个词就更新一次隐藏状态。这个隐藏状态可以理解成模型的短期记忆。

图 3：RNN 通过隐藏状态在序列中传递信息。

RNN 比固定窗口模型更灵活，因为它理论上可以把前面的信息一路传到后面。但实际训练时，它会遇到长期依赖问题。序列越长，反向传播路径越长，梯度就越容易消失或爆炸。结果是，模型很难真正记住很早之前的信息。

LSTM 在 RNN 的基础上引入了细胞状态和门控机制。遗忘门决定丢掉什么，输入门决定写入什么，输出门决定暴露什么。这样一来，信息可以更稳定地在长序列里流动。

不过，RNN 和 LSTM 都有一个绕不开的瓶颈：它们必须按顺序处理序列。第 t 步依赖第 t-1 步，天然不适合大规模并行训练。这也就引出了 Transformer。

四、Transformer：用注意力替代循环

Transformer 的关键变化，是抛弃循环结构，改用注意力机制来建模词元之间的关系。这样模型可以一次性看到整个序列，并并行计算不同位置之间的关联。

最初的 Transformer 采用 Encoder-Decoder 架构，常见于机器翻译这类任务。

图 4：Transformer 由编码器和解码器组成。

可以把它理解成两个角色：

  1. 编码器负责理解输入，把每个词元变成带上下文信息的表示。
  2. 解码器负责生成输出，根据已经生成的内容和编码器结果预测下一个词元。

真正让 Transformer 强大的，是自注意力机制。

五、自注意力：让每个词主动寻找上下文

阅读一句话时，我们不会孤立地看每个词。例如看到 “The agent learns because it is intelligent” 里的 it，我们会自然回看前面的 agent。自注意力就是把这种“回看上下文”的过程数学化。

每个词元会被映射成三个向量：

  1. Query：当前词要查询什么。
  2. Key：其他词能提供什么索引。
  3. Value：其他词实际携带什么信息。

自注意力的计算可以简化成四步：

  1. 用当前词的 Query 和所有词的 Key 计算相关性。
  2. 对相关性分数做缩放，避免数值过大。
  3. 用 Softmax 得到注意力权重。
  4. 用这些权重对 Value 加权求和，得到当前词的新表示。

Transformer 里还有几个重要组件：

  1. 位置编码：自注意力本身不知道顺序，所以需要额外注入位置信息。
  2. 前馈网络：对每个位置的表示继续做非线性变换，提取更高阶特征。
  3. 残差连接：让深层网络里的梯度更容易传递。
  4. 层归一化：稳定每一层的输入分布，提升训练稳定性。

这些模块组合起来，才构成了现代大模型的基础骨架。

六、为什么很多大模型是 Decoder-Only

今天常见的生成式模型，大多可以按 Decoder-Only / CausalLM 的思路来理解。以 Llama、Qwen 这类公开资料较多的模型为例，它们的核心目标就是预测下一个词元。GPT 系列、Claude、Gemini 这类闭源前沿模型通常不会完整公开内部架构，但从对话、代码生成、工具调用等使用方式看，也都属于“基于已有上下文持续生成下一步”的生成式范式。

这个过程也叫自回归生成：

  1. 用户给出一段输入。
  2. 模型预测下一个最可能的词元。
  3. 把刚生成的词元接回上下文。
  4. 重复预测，直到生成完整回答或触发停止条件。

这里有个关键细节：模型训练时不能偷看未来答案。所以 Decoder-Only 会使用掩码自注意力，把当前位置之后的词元遮住。这样模型在预测第 t 个词元时，只能依赖第 t 个词元之前的信息。

Decoder-Only 架构简单、目标统一、容易扩展，也天然适合对话、写作、代码生成等任务。这也是它能成为通用大语言模型主流路线的重要原因。

七、和大模型交互：Prompt 与采样参数

理解模型结构之后，再看 Prompt 会更容易。提示词不是魔法，它本质上是在给模型提供上下文、任务边界和输出格式。

常见提示方式可以按示例数量分成三类：

  1. 零样本提示：只给任务，不给示例。
  2. 单样本提示：给一个输入输出示例，让模型模仿格式。
  3. 少样本提示：给多个示例，让模型理解边界和风格。

指令调优之后，模型更擅长理解自然语言命令，所以我们可以直接写“请总结下面的内容”或者“请用 JSON 输出结果”。但在复杂任务里，示例依然很有用，尤其是格式抽取、分类、风格迁移这类场景。

采样参数决定模型如何从概率分布里选择下一个词元：

  1. Temperature 控制随机性。低温度更稳定，高温度更发散。
  2. Top-k 只保留概率最高的 k 个候选词元。
  3. Top-p 保留累计概率达到 p 的最小候选集合。

我的理解是：事实问答、代码生成、数据处理这类任务更适合低温度；头脑风暴、创意写作可以适当提高温度。Top-k 和 Top-p 通常不必同时调得很复杂，先从一个参数开始更容易观察效果。

对于需要推理的问题，思维链提示也很常见。它的核心不是让模型“装作聪明”，而是让模型把中间步骤显式展开，方便我们检查它在哪一步出错。

八、Tokenizer：看不见但很重要的一层

模型不能直接处理自然语言，它实际处理的是 Token ID。分词器负责把文本切成词元，再映射成数字。

最直观的分词方式有两种：

  1. 按词切分：语义直观，但词表会非常大，也容易遇到未登录词。
  2. 按字符切分：词表很小，但单个字符语义太弱，序列会变长。

现代大模型普遍使用子词分词，在词和字符之间折中。常见词可以保留为完整词元，低频词可以拆成多个子词片段。

BPE 是一种典型算法。它从字符级词表开始，每次合并出现频率最高的相邻片段，直到词表达到目标大小。

图 6：BPE 通过不断合并高频片段构建词表。

Tokenizer 对开发者很重要，原因有三个：

  1. 上下文窗口按 Token 计算，不按汉字数、字符数或单词数计算。
  2. API 成本通常和输入输出 Token 数直接相关。
  3. 分词结果会影响模型表现。同一段文本，多一个空格、大小写变化、符号变化，都可能切成不同的 Token 序列。

所以写 Prompt 时，除了语义清楚，也要尽量保持格式稳定。

九、本地调用开源模型的意义

通过 API 调用大模型最方便，但本地部署开源模型也很值得学习。它能帮助我理解模型、分词器、显存、推理速度之间的关系，也适合隐私敏感或离线场景。

十、模型选型不要只看“最强”

模型选型不是排行榜第一名就一定最好。实际项目里更常见的是在多个因素之间取舍：

  1. 能力：推理、代码、中文、多模态、长文本，各模型侧重点不同。
  2. 成本：闭源 API 按 Token 计费，开源部署则消耗硬件和运维成本。
  3. 延迟：实时交互场景对响应速度非常敏感。
  4. 上下文窗口：长文档、代码库分析、长期对话都依赖更大的上下文。
  5. 部署方式：API 简单，本地部署更可控。
  6. 生态：工具链、社区、微调方案和部署框架会影响开发效率。
  7. 安全性：面向真实用户时，需要考虑幻觉、偏见、越权调用和敏感信息泄露。

所以我更愿意把模型选型看成工程问题，而不是单纯的模型能力竞赛。先明确任务，再确定约束，最后才是比较模型。

十一、缩放法则与模型局限

大语言模型能力提升的背后，有一个重要经验规律：模型参数量、训练数据量和计算量增加时，模型损失通常会按可预测的趋势下降。这就是缩放法则。

但后来的研究也提醒我们，不能只堆参数。给定计算预算时，模型大小和训练数据量需要匹配。一个参数更少、数据更充分的模型，可能比一个更大但训练不足的模型表现更好。

模型变大后，还会出现一些小模型不明显的能力，比如更好的指令遵循、多步推理、代码生成和链式思考。但这并不意味着模型真正“无所不知”。它仍然有明显局限：

  1. 幻觉：模型可能编造事实，并且表达得很自信。
  2. 知识时效性：模型不知道训练数据之后发生的新事实。
  3. 偏见：训练数据里的社会偏见可能被模型学习并放大。
  4. 推理不稳定：复杂任务中，中间一步出错会影响最终答案。

从应用角度看，缓解这些问题不能只靠“写一个更好的 Prompt”。更可靠的做法是给模型接入外部知识和工具，比如 RAG、搜索、计算器、代码执行器、数据库查询和人工审核流程。

十二、这次学习后的理解

读完这部分内容后，我对大语言模型的理解从“会聊天的黑盒”变得更具体了。

从 N-gram 到词嵌入，是从统计计数走向语义表示；从 RNN 到 Transformer，是从顺序记忆走向并行注意力；从 Encoder-Decoder 到 Decoder-Only，是把生成任务统一成预测下一个词元；从 Prompt 到 Tokenizer，是理解我们如何把任务交给模型；从缩放法则到幻觉问题，则提醒我模型越强，工程约束和验证机制越重要。

如果后续要继续学习智能体，这些基础会很有用。因为 Agent 的规划、记忆、工具调用和结果校验，最后都绕不开这些问题：模型看到了什么上下文，如何生成下一步，什么时候会不可靠，以及我们该如何把它放进一个更稳的系统里。

千万级数据同步到 Elasticsearch：线程池、CountDownLatch 与背压控制

发表于 2026-05-25 更新于 2026-06-09 分类于 后端工程

项目上线前，经常会遇到一个典型场景：业务数据已经在 MySQL 里沉淀了一段时间，现在需要一次性同步到 Elasticsearch 索引库中，方便后续做搜索和查询。

如果数据量只有几万条，直接分页同步问题不大。但当数据量来到千万级，比如 1000 万条时，就不能简单地执行一次 SELECT * 把数据全部查出来。这样很容易让 Java 应用端内存被打爆，出现 OOM；同时长时间的大查询也会占住数据库连接，拖慢甚至影响线上数据库。

比较稳妥的思路是：把大任务拆成很多小批次，再通过线程池并发处理，同时用 CountDownLatch 等待所有批次结束。真正关键的地方不只是“用了多线程”，而是要用有界队列和 CallerRunsPolicy 做背压，让同步速度始终被控制在数据库、应用和 ES 都能承受的范围内。

一、核心思路：分批读取，并发写入

千万级数据同步的核心是“分而治之”。

假设数据库里有 1000 万条数据，每个批次处理 5000 条，那么整个同步任务可以拆成：

主线程只负责计算批次数，并把每个批次包装成一个任务提交给线程池。每个任务内部再完成三件事：

  1. 从数据库读取当前批次的数据。
  2. 把数据库实体转换成 ES 文档。
  3. 通过 ES Bulk API 批量写入索引。

这里有一个很重要的点：主线程提交给线程池的是任务对象，而不是一次性把 1000 万条数据读进内存。真正的数据读取发生在每个工作线程执行任务时，因此内存里同时存在的数据量会被线程数和批次大小限制住。

有界队列配合 CallerRunsPolicy，就能在消费端变慢时自动压住生产端。

五、CallerRunsPolicy 的背压控制

CallerRunsPolicy 的逻辑很简单，但效果非常关键。

当线程池的工作线程都在忙，阻塞队列也满了，主线程再次调用 executor.execute(task) 时，这个任务不会被丢弃，也不会新开无限线程，而是由提交任务的线程自己执行。

也就是说，原本只负责提交任务的主线程，会被迫停下来，亲自执行当前这个同步任务。

这个过程会带来一个天然的时间差：

  1. 主线程执行 executor.execute(task)。
  2. 线程池发现队列已满，触发 CallerRunsPolicy。
  3. 主线程同步执行 task.run()，开始查 MySQL、转换数据、写 ES。
  4. 在主线程执行任务的这段时间里，它无法继续提交新任务。
  5. 线程池里的工作线程仍然在消费队列中的任务。
  6. 主线程执行完当前任务后，executor.execute(task) 返回，继续进入下一轮 for 循环。

所以主线程不需要额外的通知机制。它执行完 run() 后，代码自然回到原来的循环位置，继续提交下一个任务。

这就是背压：当 ES 写入变慢、数据库查询变慢、工作线程消费不过来时，主线程提交任务的速度也会自动变慢。

还有一个细节：即使任务是主线程执行的，也会进入同一段 Runnable 代码，所以 finally 里的 latch.countDown() 同样会执行。只要 countDown() 放在 finally 里，就能避免某个批次异常后主线程一直等待。

这样即使出现极端情况，也不会让同步程序永久卡死。

六、线程池应该怎么选

这种场景一般使用手动创建的 ThreadPoolExecutor，不建议直接使用 Executors 提供的快捷方法。

原因在于：

  1. Executors.newFixedThreadPool() 默认使用无界队列，背压很难触发。
  2. Executors.newCachedThreadPool() 可能创建大量线程，容易把压力打到数据库和 ES 上。
  3. 灌数任务需要明确控制线程数、队列长度、线程名称和拒绝策略。

队列大小则不能太大，也不能太小。

如果队列太大，比如 10000，主线程很久都不会触发背压，系统会积压大量任务。如果队列太小，比如 10，又可能导致主线程频繁亲自执行任务，降低并发效率。一般可以从 100 到 500 之间开始压测，再根据数据库、ES 和应用内存表现调整。

自定义线程名也很重要。线上如果出现同步卡住、ES 写入失败或者数据库连接耗尽，通过 jstack、日志和监控能快速定位到 es-sync-pool-%d 这批线程，而不是面对一堆默认的 pool-1-thread-1。

2. 失败批次要能补偿

同步 2000 个批次时，只要有几个批次因为网络抖动、ES 瞬时拒绝写入或数据库超时失败，就可能造成索引数据缺失。

所以 catch 里不能只打印日志。更稳妥的方式是把失败批次记录下来，例如写入失败表、Redis 或本地补偿文件，主流程结束后再进行二次重试。

同时，写 ES 时最好保证幂等。比如使用数据库主键作为 ES 文档 _id，重复写入同一条数据时只是覆盖更新，而不是生成重复文档。

3. Bulk 大小要压测

每批 5000 条只是一个经验值，不是固定答案。

如果单条文档很大，5000 条可能会让单次 Bulk 请求过重，导致 ES 写入慢或者请求体过大。如果单条文档很小，批次太小又会导致网络请求过多，吞吐上不去。

实际落地时要观察几个指标：

  1. 单次 Bulk 请求耗时。
  2. ES 是否出现拒绝写入。
  3. JVM 堆内存和 GC 情况。
  4. MySQL 查询耗时和连接池占用。

然后再调整 pageSize、线程数和队列长度。

4. 数据库压力可能成为瓶颈

线程池开到 CPU * 2 并不代表一定合适。它只是一个起点。

如果压测发现 MySQL CPU 飙高、慢查询增多，或者连接池被打满，就要降低并发线程数，或者增大单批次大小，减少并发查询次数。同步任务的目标不是让应用跑满，而是让数据库、应用和 ES 形成稳定吞吐。

八、总结

千万级数据同步到 Elasticsearch，重点不是简单地“开多线程”，而是建立一个可控的同步流水线。

CountDownLatch 解决的是主线程如何等待所有批次结束；ThreadPoolExecutor 解决的是并发执行；有界队列和 CallerRunsPolicy 解决的是生产速度过快时如何自动减速。

一套比较完整的方案应该同时考虑：

  1. 分批读取，避免一次性加载导致 OOM。
  2. 有界线程池，限制并发和任务积压。
  3. CallerRunsPolicy，在消费变慢时形成背压。
  4. CountDownLatch，等待所有批次完成，并设置超时。
  5. ID 滚动分页，避免 MySQL 深分页问题。
  6. 失败批次记录和重试，保证最终数据完整。
  7. 使用数据库主键作为 ES _id，保证重复写入时具备幂等性。

这样设计后，整个同步任务就不再是一次不可控的大查询，而是一批批可观察、可限流、可补偿的小任务。

分布式路由追踪：从 TraceId 到跨线程透传

发表于 2026-05-23 更新于 2026-06-09 分类于 后端工程

在排查线上问题时，最怕看到的是一串散落在不同机器、不同服务、不同线程里的日志：每一条看起来都和问题有关，但又很难串成一条完整的请求链路。

分布式路由追踪要解决的就是这件事：给一次请求一个全局唯一的 TraceId，让它在网关、业务服务、RPC 调用、消息队列、异步线程之间一直传下去。这样排查问题时，就可以根据一个 TraceId 找到完整路径，再结合每个关键步骤的耗时和调用关系定位问题。

一、为什么需要 TraceId

在单体项目里，请求通常只落在某一台机器上的某个进程里。只要日志里能打印出请求标识，基本就可以顺着日志找到整个执行过程。

但在微服务环境下，一次请求可能会经过：

  1. 网关。
  2. A 服务。
  3. B 服务。
  4. MQ 消费者。
  5. 线程池里的异步任务。

如果没有统一的追踪标识，这些日志就会分散在不同服务、不同机器甚至不同线程中。排查问题时只能到处搜索，效率很低。

所以，最基础的做法是引入 TraceId。它代表一次完整请求。只要所有服务都把同一个 TraceId 打进日志，就能把散落的日志重新串起来。

不过，只有 TraceId 还不够。它可以告诉我们“这些日志属于同一次请求”，但不一定能告诉我们“服务之间是如何调用的”。这时还需要 SpanId。

二、TraceId 和 SpanId 分别做什么

可以这样理解：

  • TraceId：标识一整条请求链路。
  • SpanId：标识链路中的某一次调用或某一个执行片段。

比如一次请求从网关进入 A 服务，A 服务再调用 B 服务，B 服务又调用 C 服务。它们拥有同一个 TraceId，但每一次调用都应该有不同的 SpanId。

这样不仅能知道日志属于哪次请求，还能知道调用层级和先后关系。

三、先从单体场景做日志增强

在单体或集群部署的场景里，首先要解决的是“如何无侵入地打印追踪日志”。

需求通常有两个：

  1. 对业务代码尽量无侵入。
  2. 对接口性能影响尽量小。

无侵入可以通过切面编程实现。切面可以分成两类：

  • 静态代理：典型代表是 AspectJ，在编译期完成切面代码注入。
  • 动态代理：典型代表是 Spring AOP，在运行期生成代理对象，再通过代理和反射完成增强。

如果只是做日志记录、限流、耗时统计这类通用增强，静态代理对运行时性能影响更小。动态代理虽然更灵活，但运行期生成代理类和反射调用会带来一定开销。

如果并发量比较高，还要考虑日志量。假设系统有 10000 QPS，每个请求打印 10 条日志，每秒就会产生 10 万条日志，对磁盘 IO 压力很大。对于 INFO 级别日志，可以做采样，比如只记录 10%。对于异常日志，则应该尽量完整保留。

还有一个实际问题：集群里有多台实例时，不知道某个 TraceId 的日志落在哪台机器上。如果每次都登录多台机器搜索，会很痛苦。更好的做法是把日志发送到消息队列，再由消费端写入 Elasticsearch。排查问题时直接在 ES 中按 TraceId 检索即可。

四、微服务场景：让 TraceId 在服务之间传递

进入微服务后，问题变成了：一次请求跨越多个服务，TraceId 怎么传下去？

基本流程是：

  1. 网关收到外部请求时生成全局唯一的 TraceId。
  2. 网关把 TraceId 放入请求 Header。
  3. 业务服务的 Filter 拦截请求，从 Header 里解析 TraceId。
  4. 服务把 TraceId 放入当前线程的 RequestContext。
  5. 后续 RPC、MQ、异步任务继续从 RequestContext 中读取并透传。

RequestContext 通常基于 ThreadLocal 实现。这样当前请求线程里的业务代码都可以方便地获取 TraceId，而不需要在每个方法参数里显式传递。

在服务之间传递时，常见场景有两类：RPC 调用和消息队列。

因此可以借鉴它的思路，自己做一个更小范围的透传实现。

核心原则是：

  1. 提交任务时，从当前线程复制需要透传的字段。
  2. 执行任务前，把这些字段设置到子线程的 ThreadLocal。
  3. 任务执行结束后，清理子线程上下文。

九、一次完整链路可以这样串起来

把上面的内容合在一起，一次请求的追踪流程大概是：

  1. 请求进入网关，网关生成 TraceId。
  2. 网关把 TraceId 写入 Header，转发给业务服务。
  3. 业务服务 Filter 解析 Header，写入 RequestContext。
  4. 方法切面记录接口耗时、成功状态和异常信息。
  5. Dubbo 调用前把 TraceId 写入 attachment。
  6. Dubbo 服务提供方从 attachment 中恢复 TraceId。
  7. MQ 发送和消费时通过消息属性继续传递 TraceId。
  8. 线程池任务通过 TaskDecorator 复制上下文。
  9. 特殊异步任务使用 RunnableWrapper 或 CallableWrapper 手动透传。
  10. 日志统一进入 MQ 和 ES，排查时按 TraceId 检索。

这条链路里最重要的不是某一段代码，而是两个动作：入口处生成，边界处透传。

入口包括网关、MQ 消费入口、定时任务入口等。边界包括 RPC、MQ、线程池、手动创建线程等。只要每个边界都处理好，TraceId 就不会轻易断。

十、总结

分布式路由追踪的核心目标，是让一次请求在复杂系统里仍然保持“可观察”。

在实现上，可以分层推进：

  1. 用 AOP 记录方法耗时和执行结果，降低业务侵入。
  2. 用日志采样和集中式检索降低 IO 与排查成本。
  3. 用 TraceId 串联同一次请求的所有日志。
  4. 用 SpanId 补充服务间调用关系。
  5. 用 RPC Filter 和 MQ Header 解决跨服务传递。
  6. 用线程池装饰器和任务包装器解决跨线程传递。

真正容易出问题的地方，往往不是主流程，而是各种边界：服务调用边界、消息边界、线程边界。把这些边界守住，链路追踪才能从“日志里有个 ID”变成真正可用的排查工具。

  3. 仓库根目录是否真的有 index.html。
  4. Actions 或仓库首页的 Checks 是否有失败项。
  5. Hexo 静态站点是否包含 .nojekyll。

这次问题解决后，我更清楚地理解了：hexo deploy 只是把文件推到 GitHub，真正让网站可以访问，还需要 GitHub Pages 成功完成发布流程。
